# Phase 1.3 Design — Family conventions

**Date:** 2026-10-31
**Phase:** 1.3
**Surface:** Refactor
**Stage:** phase (one phase, implementation-ready)

## Goal

Ariadne.NET adopts the ZeroAlloc conventions its Cretan family siblings already use: expected failures come back as `Result<T, AriadneError>` instead of exceptions, the build has zero analyzer warnings and fails on any new one, and ZeroAlloc.Inject, Validation, Telemetry and Resilience replace hand-rolled or outdated equivalents.

## Intent and scope

Nothing is published yet, so changing public signatures costs nothing now and a major version after Phase 1.4. The siblings set the shape: Mnemosyne.NET puts `MnemosyneError` and ZeroAlloc.Results in its Abstractions package, Rag.NET puts `[Validate]` rules on its Abstractions models, and Minos.NET instruments its operations with ZeroAlloc.Telemetry. The user asked to use as many ZeroAlloc libraries as genuinely fit, and to drop the ones that only fit through a workaround.

**Goals:**
- Expected failures in the pack pipeline and sync return `Result<T, AriadneError>`.
- The analyzer run is clean, and `TreatWarningsAsErrors` keeps it that way.
- `ZInject` 0.10.5 is replaced by ZeroAlloc.Inject. `ZInject` is the old, abandoned name of that package: the last ZInject release is 0.10.5, and ZeroAlloc.Inject is at 1.11.6.
- ZeroAlloc.Validation checks rule packs when they load, ZeroAlloc.Telemetry instruments the pack and sync operations, and ZeroAlloc.Resilience puts a timeout and retry around git.
- `Ariadne.NET.Abstractions` stays Native AOT-clean with its new dependencies.

**Non-goals:**
- Converting validation (`ISourceValidator`, `ILinter`, `IDependencyValidator`), generation (`IGenerateOrchestrator`, `IWorkspaceOrchestrator`, `ICodeGeneratorService`) or `ILayerInferenceEngine`. M2.1 reshapes validation onto a Roslyn compilation, and M5 decides code generation's role. They keep their current shapes until then.
- Making the engine AOT-safe. Roslyn Workspaces and YamlDotNet still rule it out, and the CLI and MCP depend on the engine.
- ZeroAlloc.Cache. Its generator caches only `Task<T>` and `ValueTask<T>` methods (diagnostic ZC0005), and `IBuiltinPackRegistry.GetPack` is a synchronous embedded-resource read. Making it async only to fit the cache would be a workaround. Cache is noted on Phase 6.2, where packs are fetched over the network.
- Serialisation (Phase 3.2 reports), Specification (Phases 2.2 and 2.3 rule matching) and TestHelpers (Phase 2.1 hot paths). These are noted on those phases.
- Replacing YamlDotNet. That is still the separate, unscheduled project recorded in STATE.md.
- CI. Phase 1.4 adds the build, the tests and the AOT smoke publish to CI.

**Anti-goals:**
- `Try*` twins next to throwing methods. This would keep the behaviour the phase removes and double the API.
- A `catch (Exception)` that turns bugs into `AriadneError`s. Only expected failures become Results, and a bug still throws.
- Warnings silenced with `NoWarn` or `#pragma` to reach zero. Each one is fixed at its source. A suppression is acceptable only where the analyzer is provably wrong, and then it is local, carries a justification comment, and is listed in the plan's review notes.
- A Results conversion that leaves an exception path reachable for an expected failure, such as an unknown pack name or malformed YAML.

## Decisions

Decided with the user on 2026-10-31:

1. **Scope of Results: the pack pipeline and sync.** These are `IRulePackLoader`, `IRulePackResolver` and `IBuiltinPackRegistry` (in Abstractions) and their implementations, `TemplateReference`, `IImportsLoader` with `ImportsYamlLoader`, `SemVerRange` parsing, and `ISyncOrchestrator` with `IGitSyncProvider`. The CLI and MCP surfaces map the errors.
2. **Mnemosyne-style error.** `AriadneError` is defined in `Ariadne.NET.Abstractions` as follows:
   ```csharp
   public readonly record struct AriadneError(AriadneErrorCode Code, string Message, string? Detail = null);
   public enum AriadneErrorCode { NotFound = 1, Invalid = 2, Unavailable = 3 }
   ```
   The values are numbered from 1, so the `default` error of a `default` Result reads 0 and is recognisable as never set. Mnemosyne documents the same reasoning on `MnemosyneErrorCode`.
3. **Analyzers: zero warnings, enforced.** Upgrade ZeroAlloc.Analyzers from 1.0.3 to the latest 1.11.x, fix all findings, and set `TreatWarningsAsErrors` in `Directory.Build.props`. A trial upgrade to 1.11.3 reports 5 ZeroAlloc findings: ZA0108 in `RulePackMerger.cs:82` and ZA0208 four times in `GitCliSyncProviderTests.cs`. Together with the 27 baseline warnings that makes 32: HLQ005 ×7, MA0006 ×10, MA0051 ×2, and EPC12, EPS06, HLQ012, MA0009, MA0048, MA0096, MA0097 and ZI007 once each. Almost all are in tests.
4. **Inject:** move from ZInject to ZeroAlloc.Inject (and ZeroAlloc.Inject.Generator) at the latest 1.11.x.
5. **Validation on the Abstractions schema types.** Put `[Validate]` and rule attributes directly on the six schema types, following Rag.NET.Abstractions. Abstractions then depends on `ZeroAlloc.Results` and `ZeroAlloc.Validation`, with `ZeroAlloc.Validation.Generator` as `PrivateAssets="all"`. This relaxes Phase 1.2's "no package references" rule in a deliberate, documented way.
6. **Telemetry and Resilience are in scope.** Cache is deferred to 6.2.

## Approaches

| Approach | Trade-off | Outcome |
|---|---|---|
| Change the existing signatures in place to return Results | One breaking change while nothing is published; every caller updates once | **Chosen.** Nothing is published, and the alternatives keep the old behaviour alive |
| Add `Try*` methods beside the throwing ones | No caller churn, but two APIs, and the throwing one stays the default | Rejected: this is the anti-goal above |
| Wrap at the surfaces only (CLI and MCP catch and map) | Smallest diff, but library consumers such as roslyn-codelens in M6.1 still get exceptions | Rejected: it misses the DoD line "public engine APIs return Results" |

For Validation, the alternative was internal YAML document types in the engine, mapped onto the Abstractions types with ZeroAlloc.Mapping. That would keep Abstractions on Results only, at the cost of a second model of every schema type just before M2.2 redesigns the schema. The user chose the attributes on the Abstractions types.

For Cache, the alternative was to make `IBuiltinPackRegistry` async (`ValueTask<Result<RulePack, AriadneError>> GetPackAsync`) so `[Cache]` could attach. The user deferred Cache to 6.2 instead.

## Design

### Error model and codes

| Failure | Code | Message and detail |
|---|---|---|
| Unknown built-in pack | NotFound | Message names the pack, Detail lists the available packs |
| Import not in the manifest (`SyncByNameAsync`) | NotFound | |
| Imports file or pack file does not exist | NotFound | Detail holds the path |
| Import cache directory missing, or it has no YAML (resolver `import://`) | NotFound | Message says to run `ariadne sync` |
| `import://` with no working directory | Invalid | |
| Malformed YAML (YamlDotNet `YamlException`) | Invalid | Detail holds the line and column from the exception's `Start` mark |
| Pack fails `[Validate]` rules | Invalid | One error. Message summarises, and Detail lists every failure as `path: reason`, as Mnemosyne words validation messages |
| Unsupported `extends` scheme | Invalid | |
| Template expression with no names | Invalid | |
| Bad semver range in imports | Invalid | |
| Unsupported import type (anything other than `git`) | Invalid | |
| No tag satisfies the version range | NotFound | |
| git fails, times out or exhausts retries | Unavailable | Detail holds git's stderr or the policy failure |
| IO failure reading or writing the cache | Unavailable | Detail holds the exception message |

`ArgumentNullException` guards stay as throws: a null argument is a caller bug, not an expected failure. A missing embedded resource in `BuiltinPackRegistry`, when the resource map names it but the assembly lacks it, is a packaging bug and stays a throw (`InvalidOperationException`). So does the same case in the MCP `PackResources`.

The resolver stops at the first failing `extends` reference and returns its error. Collecting every failure is not needed: the user fixes one reference and runs again.

### Signatures (target shape)

```csharp
// Ariadne.NET.Abstractions
Result<RulePack, AriadneError> LoadFromString(string yaml);
Result<RulePack, AriadneError> LoadFromFile(string filePath);
Result<RulePack, AriadneError> Resolve(RulePack userPack);
Result<RulePack, AriadneError> Resolve(RulePack userPack, string? workingDirectory);
IReadOnlyList<string> GetAvailablePackNames();      // unchanged, cannot fail
Result<RulePack, AriadneError> GetPack(string name);

// Engine
Result<IList<string>, AriadneError> TemplateReference.ParseNames(string template);
Result<IList<string>, AriadneError> TemplateReference.ToExtends(string template);
Result<ImportsManifest, AriadneError> IImportsLoader.LoadFromString / LoadFromFile
Result<SemVerRange, AriadneError> SemVerRange.Parse(string range)   // name per builder
Task<IReadOnlyList<ImportSyncOutcome>> ISyncOrchestrator.SyncAllAsync / SyncByNameAsync
Task<Result<SyncedImport, AriadneError>> IGitSyncProvider.SyncAsync
```

The builder may use the exact ZeroAlloc.Results 1.4.5 type names (`Result<T, E>`, `UnitResult<E>`) and helper idioms as the library offers them. The return shapes above are the contract.

**Sync shape.** `SyncResult` loses `Success` and `Error`. The successful data (`ImportName`, `ResolvedVersion`, `WasCached`, `CachePath`) becomes `SyncedImport`. Each import in a sync-all run succeeds or fails on its own, so the orchestrator returns a list with one outcome per import. Each outcome pairs the import name with `Result<SyncedImport, AriadneError>` (`ImportSyncOutcome`, name per builder). One failing import does not stop the others, which matches today's behaviour. `SyncByNameAsync` with an unknown name returns a single NotFound outcome, as today. `SyncedImport` and the outcome type are `sealed record`s *(my call)*: they hold strings and a Result, and do not sit on a hot path. The CLI keeps the output and exit behaviour of `SyncCommand` today:
- one line per import, with failures on stderr as `name FAILED: {Message}`;
- a closing count line;
- `ExitCodes.Error` if any outcome failed, otherwise `ExitCodes.Success`.

**No YAML-converter calls.** `TemplateReference` is called only from `InitCommand` and `RuleResolutionHelper`, and `SemVerRange.Parse` only from `GitCliSyncProvider`. None of them runs during deserialisation, so their Results propagate normally.

### Surfaces

- **CLI:** every `AriadneError` prints `Error: {Message}`, plus Detail on the next line when present, to stderr, and exits with `ExitCodes.Error` (2). Exit code 1 keeps meaning "violations found". The catch-all in `CliRootCommand.Invoke` stays, for real bugs only. `RulesCommand`'s own `FileNotFoundException` becomes a Result-driven error path. `InitCommand`'s `registry.GetPack(name); // throws if not found` becomes an explicit check of the Result.
- **MCP:** tools and resources that resolve packs return the error as a tool error result (`IsError = true` with the message and detail as text) instead of letting an exception escape. `RuleResolutionHelper` returns a Result, and each tool maps it. The builder uses whatever error-result idiom the ModelContextProtocol 1.1.0 SDK offers for tools and resources.

### Validation

`[Validate]` goes on `RulePack`, `LayerDefinition`, `ComponentRoleDefinition`, `CodeFeatureRuleDefinition` and `NamingConventions`. The rules cover what the engine already assumes when it uses a pack. Required names are not empty, and a layer's `dependsOn` and a role's layer refer to layers that exist. Per-member checks use the built-in attributes. Cross-reference checks live in the resolver, as described below. The builder derives the exact rule list from what the engine dereferences today (for example, where the merger or inference would hit a null or a missing key) and lists it in the plan. **No new rule may reject any built-in pack** (`clean-architecture`, `hexagonal-architecture`, `cqrs`), nor any pack in the test fixtures.

Validation runs at two points:
- **In the loader**, after deserialising: the generated `[Validate]` validators, which carry structure and per-member rules only. `LoadFromString`, `LoadFromFile` and `BuiltinPackRegistry.GetPack` (which goes through the loader) therefore check structure only.
- **In the resolver, on the merged pack:** cross-reference checks, such as a `dependsOn` naming an existing layer, or a role's layer existing.

A user pack that only adds roles on top of a built-in pack is not complete by itself, so cross-reference rules apply to the merged result, not to a lone partial pack. *(my call)* For that reason the cross-reference rules are **not** `[CustomValidation]` attributes on `RulePack`. The generated `RulePack` validator would run them at load time and reject partial packs. They live instead in an engine-side check (for example an internal `RulePackReferenceCheck` returning `Result<RulePack, AriadneError>`) that only the resolver calls. `Resolve` always runs it, including when the pack has no `extends`, because then the user pack is the complete pack.

The test "all three built-in packs pass" resolves a pack that `extends` each built-in, so it covers both the loader rules and the cross-reference check.

The generated validators register through `ZeroAlloc.Validation.Inject` if it works with ZeroAlloc.Inject in this setup. Otherwise the loader and resolver construct them directly. The builder decides which.

### Telemetry

Following Minos.NET (`IDecisionEvaluation`), the instrumented interfaces are **internal to the engine** and wrap the public operations, so Abstractions takes no Telemetry dependency. ZeroAlloc.Telemetry's own docs note that an abstractions assembly is where an extra dependency is least welcome. One ActivitySource and Meter is named `Ariadne.NET`, exposed as a public constant so hosts can subscribe.

The instrumented operations are: load (from file and from string), resolve, get built-in pack, and sync import. *(my call)* The git commands get no span of their own. The sync-import span wraps the whole resilient git call, retries included, so one span covers each import, and every failure carries an `AriadneError` code. This avoids stacking a Telemetry proxy and a Resilience proxy on the same `IGitClient`, and avoids a second error vocabulary (`ResilienceError`) in the metric tags. Each operation gets a span, and spans are failures when `IsFailure` (`ErrorWhen = "IsFailure"`). Each gets a duration histogram tagged with the error code on failure (`MetricTagFromResult`). Tags carry pack and import names, never file contents. Memory notes from earlier family work apply:
- The generated proxy is `internal sealed` by default, which is fine here because everything stays inside the engine.
- `[Count]` counts only non-throwing calls.
- Since Telemetry 1.12.6, a cancelled call is recorded as an error. A later Telemetry fix stops recording a caller's cancellation as an error, so use the latest version.

The public engine services delegate to the instrumented internal operations. Proxies register through ZeroAlloc.Inject. The builder chooses between a decorator registration and explicit construction, depending on what ZeroAlloc.Inject 1.11.x supports for generated proxies.

### Resilience

ZeroAlloc.Resilience's `[Retry]` reacts only to exceptions, and a returned failed `Result<T, E>` with a foreign `E` passes through untouched (Resilience docs, "Foreign error types"; issue ZeroAlloc-Net/ZeroAlloc.Resilience#142). So the policy sits on a new **internal `IGitClient`** that only runs git commands. Its implementation throws on a non-zero exit, as `RunGitAsync` does today. Its interface returns `ValueTask<Result<string, ResilienceError>>`, so the generated proxy turns a timeout, an exhausted retry or a throw into a returned `ResilienceError` failure without throwing. `GitCliSyncProvider` maps that failure to `AriadneError` Unavailable, with git's stderr in Detail.

Policy *(my call)*: `[Timeout(Ms = 60_000)]` per git command, and `[Retry(MaxAttempts = 3, BackoffMs = 500)]`. A wrong URL or a failed authentication is retried pointlessly, since git's exit codes don't separate transient from permanent failures. The cost is about a second, which is acceptable. A caller's cancellation must propagate as `OperationCanceledException` and must not be retried or turned into a failure. The builder verifies how the Resilience proxy treats a cancelled token and adds a test for it.

### AOT

Abstractions keeps `IsAotCompatible`. `tests/Ariadne.NET.AotSmoke` is extended to load a pack type, run its generated validator and build an `AriadneError` Result. It must still publish with `-p:PublishAot=true -warnaserror`. If ZeroAlloc.Validation or Results brought an AOT warning into Abstractions, that would be a real problem to fix at its source, not suppress. ZeroAlloc libraries are AOT-ready by design, so none is expected.

## Tests

- **Unit, Results:** every row of the error table has a test asserting the code, and the message or detail where it matters. Examples: unknown pack gives NotFound with the available names, malformed YAML gives Invalid with a line number, unsupported scheme gives Invalid, missing cache gives NotFound, and git failure gives Unavailable (through a fake `IGitClient`).
- **Unit, Validation:** each rule has a passing and a failing case. All three built-in packs load and resolve successfully, which guards against over-strict rules.
- **Unit, Telemetry:** an `ActivityListener` and `MeterListener` test proves a failed resolve produces an error span tagged with the error code, and a successful one does not.
- **Unit, Resilience:** a fake inner git client that throws twice and then succeeds shows the retry. One that always throws produces Unavailable, not an exception. A cancelled token propagates `OperationCanceledException`.
- **Surface:** CLI tests assert exit code 2 and the stderr message for a NotFound, an Invalid and an Unavailable case. MCP tests assert a tool error result, not an exception, for an unknown pack.
- **Regression:** the existing 263 tests stay green, with their callers updated to the Result shapes. A `dotnet build --no-incremental` gives zero warnings. The AOT smoke publish passes. `dotnet pack` still yields exactly `Ariadne.NET` and `Ariadne.NET.Abstractions`, and the Abstractions nuspec lists only ZeroAlloc.Results and ZeroAlloc.Validation as dependencies. A nuspec lists direct dependencies only, and the generator is `PrivateAssets`. ZeroAlloc.Validation.Inject, if used, is an engine reference, not an Abstractions one. The suite has 12 exception assertions (`Throws`), most in the converted area, and these are rewritten to assert the returned error.

## Open Questions

None blocking. Items left to the builder are marked in the sections above: exact ZeroAlloc type and idiom names, the Validation rule list and where each rule runs, how proxies and validators register with ZeroAlloc.Inject, the MCP error idiom, and Resilience's cancellation behaviour.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| ZeroAlloc.Inject 1.11 differs from ZInject 0.10.5 (attribute names, generated method names, diagnostics such as the current ZI007) | Build breaks across all projects | Migrate Inject first, as its own task, with the full test suite green before anything else changes |
| Validation rules reject packs that work today | Users' packs break on upgrade | The built-in packs and test fixtures must pass. Rules are derived from what the engine already dereferences, not from wishes |
| Cross-reference validation on a partial user pack | False Invalid for packs that rely on `extends` | Cross-reference rules run on the merged pack in the resolver |
| `TreatWarningsAsErrors` blocks later tasks mid-phase | Work stalls on unrelated warnings | Turn it on in the analyzer task after all 32 warnings are fixed. Later tasks keep the build at zero |
| Telemetry and Resilience proxies don't compose with ZeroAlloc.Inject registration | Generated proxy not used, so no spans and no retry | Tests assert spans and retries through the DI-built service, not only on a hand-constructed proxy |
| A Results conversion misses a throw path for an expected failure | The DoD line reads true but isn't | refactor-analysis lists every throw site in the converted area. The plan's final review checks each one against the error table |
