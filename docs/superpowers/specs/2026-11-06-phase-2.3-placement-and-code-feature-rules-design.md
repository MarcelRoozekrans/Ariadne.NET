# Phase 2.3: Enforce placement and code-feature rules

**Surface:** Backend
**Status:** approved 2026-11-06
**Milestone:** 2, Rule engine v2. Builds on `2026-11-04-milestone-2-design.md` and `2026-11-05-phase-2.2-rule-schema-v2-design.md`.

## Intent

A pack can say which layer a kind of type belongs in and what shape it must have, and the engine enforces that on the real type graph. `CODE-001` and `CODE-002` come from the pack instead of being hard-coded checks whose ids no longer exist in the source.

Today the only placement logic is `RoleRules`: a role matches a type whose name ends with the role name, but only inside the role's own layer, so a `*Repository` class in the wrong layer is never noticed. Three fixed checks hang off role fields (type kind, `internal` accessibility, missing interface) and report `role/<Name>`. Selectors know namespace, assembly and type name only; 2.2 left base type, interface and attribute for this phase.

## Goals

1. `TargetSelector` gains `baseTypes`, `interfaces` and `attributes`, usable everywhere a selector is: `forbid`, `allowOnly` and the new rule.
2. A new rule kind, `require`, says that every type a selector picks must satisfy some requirements: sit in a layer, be of a kind, have an accessibility, implement an interface.
3. `componentRoles` stay in the schema and are expanded into `require` rules when the pack loads. One matching engine serves both.
4. `CODE-001` and `CODE-002` are rule ids in the pack model. Violations report them, with their `because`.
5. Every violation of these rules carries the rule id and the `because`, as the 2.2 rules do.

## Non-goals

- Vacuity detection and `allowEmpty`: phase 2.5. Until then a `require` rule that matches nothing is silent, as `forbid` is today.
- Banned packages, member-level forbidden APIs, name collisions: phase 2.4.
- Naming conventions stay with code generation and are not validated.
- No new breaking change to the schema or to `componentRoles`. This phase adds a rule kind and selector keys.
- Module isolation stays in #32.

## Anti-goals

- A phase that makes the ten built-in packs noisy on ordinary solutions. Roles such as `Service` or `Handler` match common names, so nothing in a built-in pack may start failing existing solutions by default.
- Two matching implementations, one for roles and one for rules.

## Constraints

- Selectors are ordinal and case-sensitive, and lists AND together while the values in a list OR, as in 2.2. A selector with no list matches every type, so the loader still rejects an empty selector.
- The checks are open-world. A type that no layer covers is not a violation of a layer requirement unless the rule selects it explicitly.
- Generated code is not a subject, as in 2.1.
- Only source types are checked. Enums and delegates were never matched by roles and stay out.
- The strict loader rejects unknown keys. Every new key needs a message in pack terms, with line and column.
- No local AOT publish and one build or test at a time on the shared VM.

## Approaches

1. **One `require` rule, roles kept as shorthand (chosen).** Roles expand into `require` rules at load. No schema break, one matching engine, the ten built-in packs keep working. The cost is two ways to write one constraint.
2. **Two rule kinds, `placement` and `codeFeature`, as the roadmap words it.** Closest to the roadmap text but writes selector matching twice. Rejected.
3. **Replace roles with `require` rules.** One vocabulary, but a second `feat!` right after 2.2 made roles strict, and all ten built-in packs are rewritten. Rejected.

## Design

### Selector keys

`baseTypes`, `interfaces` and `attributes` are lists of type-name globs, using the `types` glob rules.

- **`baseTypes`** matches when any class in the type's base chain, excluding `object`, matches.
- **`interfaces`** matches when any interface the type implements matches, including inherited ones, so an interface's own interfaces count.
- **`attributes`** matches when an attribute class applied to the type matches. The glob is against the attribute's full name, so `**.ObsoleteAttribute` and `System.ObsoleteAttribute` match `[Obsolete]`; the pack author writes the real class name.
- On a rule's `to` selector the same keys select dependency targets, so `forbid` can bar a layer from anything implementing `IDisposable`-style marker interfaces. Layer entries do not accept the new keys, as they do not accept `types`.

### The `require` rule

```yaml
rules:
  - id: CA-REPOSITORIES-IN-INFRASTRUCTURE
    require:
      for: { interfaces: ["**.I*Repository"] }
      layer: Infrastructure
      kind: Class
      accessibility: internal
      implements: { types: ["**.I*Repository"] }
    exceptions: [...]
    locked: false
    because: Persistence belongs to Infrastructure.
```

- `for` is a selector, required, and must not be empty.
- At least one of `layer`, `kind`, `accessibility`, `implements` is required. `layer` names a layer of the merged pack. `kind` and `accessibility` take the values roles take today. `implements` is a selector over interfaces: the selected type must implement at least one interface it matches.
- A rule yields one violation per selected type and failed requirement. The violation kinds are the existing `TypeKindMismatch`, `AccessibilityMismatch` and `MissingInterface`, plus a new `WrongLayer`.
- `exceptions` work as on `forbid`: a type an exception names is not a subject. `locked` and the merge rules are unchanged from 2.2.

### Roles expand into rules

At merge time, after roles are resolved, each role becomes rules of the same engine:

- A role selects types by name suffix inside its layer, as today. Matching stays case-insensitive and runs on the simple type name, as `RoleRules.MatchRole` does now: the expansion marks the generated selector as name-suffix, case-insensitive, an internal mode that is not a pack key. Explicit selectors stay ordinal and case-sensitive.
- A type gets at most one role, as today: the generated selector of a role excludes the types an earlier role of the same layer matches, in the order the merged pack lists them.
- `ROLE-<Name>` carries the role's `kind` requirement only.
- `CODE-001` and `CODE-002` are two synthesized, locked rules per merged pack. `CODE-001` is today's missing-interface check; `CODE-002` is today's accessibility check, the roles with `accessibility: internal`. Each is present when at least one role needs it. They split the checks between them, so one failed requirement is never reported under two ids. Their `because` text is fixed by the engine and the violation message names the role.
- Role descriptions become the `because` of `ROLE-<Name>`; an empty description falls back to `Role '<Name>' defines this shape.`.
- Ids starting `ROLE-` or equal to `CODE-001`, `CODE-002` are reserved. A pack that declares one fails the load with a message that names the reserved id. Expansion runs once on the merged pack, after the 2.2 merge and role resolution, and before the reference check.
- Violations that used to report `role/<Name>` now report the rule id. Nothing in the engine or the CLI keys on the old ids, so this changes output text and tests only, and goes in the release notes.
- Violation ordering stays as in `RoleRules`: located violations first, ordered by location, rule id, source type and kind, then unlocated ones.

### Placement

Placement is explicit. A `require` rule with `layer` flags a selected type that no layer covers or that sits in another layer. A rule that selects a type explicitly overrides the open-world default: the author named the type, so an uncovered one is a violation. Overlapping layers are already a `LayerOverlap` error, so a type has one layer. Roles do not assert placement on their own, because that would make every `*Service` outside its layer a violation of every built-in pack, which is the anti-goal above.

### Requirement semantics

- `kind` and `accessibility`: enums and delegates are never subjects of `kind`, `accessibility` or `implements`; only `layer` applies to them. `accessibility` keeps today's logic: `internal` requires `Accessibility.Internal` exactly, `public` is the default and requires nothing.
- `implements` accepts `types`, `namespaces` and `assemblies`, not the three new keys. It counts every interface of the type, including those it gets through a base class.

### Where it lives

- **Abstractions** (additive): `TargetSelector` gains three lists, `RuleKind` gains `Require`, `RuleDefinition` gains the requirement fields. No `feat!`.
- **Engine:** `TypeSelector` learns the three keys and the `TypeGraph` exposes base chain, interfaces and attributes per type, built once per type like the namespace cache. A `RequireRules` checker sits next to `ForbidRules`. `RoleRules` shrinks to expansion. `ViolationKind` gains `WrongLayer`.
- **Loader:** new keys, new rule kind, messages for the cases above, and the role expansion in `RulePackMerger`.
- **Surfaces:** CLI `rules`, MCP `get_rules` and `get_layers` show `require` rules and the expanded role rules; CLI `validate` and MCP `validate_source` report the new kinds.
- **Docs:** the pack reference page, the rule-schema page and one worked placement example. This repository's `.architecture/rules.yaml` gains placement rules as dogfood; the built-in packs gain none.

## Decisions by the owner, 2026-11-06

- **`CODE-001` keeps today's meaning.** It stays a solution-wide check: it fails a role that requires an interface when no type in the solution matches the role's `interfaceRole`. It lives inside the synthesized `CODE-001` rule as an engine check, not as a key of `require`, so no solution that passes today starts failing. Tightening it to a per-type check is a later, separate change.
- **No placement rules in the ten built-in packs in this phase.** The phase ships the `require` rule, the selector keys and a worked docs example. Placement rules are added to this repository's `.architecture/rules.yaml` as dogfood. Built-in packs get theirs once they have proven quiet on real solutions.
- **Overall approach:** one `require` rule with roles kept as shorthand (approach 1).
