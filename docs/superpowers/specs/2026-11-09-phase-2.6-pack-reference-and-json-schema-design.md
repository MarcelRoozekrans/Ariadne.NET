# Phase 2.6 Design — Pack reference and JSON Schema

**Date:** 2026-11-09
**Phase:** `2.6`
**Surface:** `Docs`
**Stage:** phase (one phase, implementation-ready)
**Status:** draft

Milestone 2, Rule engine v2. Builds on `2026-11-04-milestone-2-design.md`. Phases 2.1 to 2.5 are complete, so nothing here waits on an unfinished phase.

## Goal

Every v2 rule type has a reference entry on the docs site, a JSON Schema gives editors validation and completion for packs, and the drifted `docs/how-it-works/` copy is deleted.

## Intent and why

Phases 2.2 to 2.5 changed the pack format four times, and the docs-site rule-schema page was kept current through all of them. What is missing is a reference a pack author can look a rule type up in, and tooling that tells them about a typo before they run the tool. The loader is strict and rejects unknown keys, so a wrong key is already an error at run time; the schema moves that error into the editor. The old `docs/how-it-works/` copy still describes removed features and has to go before it misleads anyone, and `CLAUDE.md` still tells contributors to keep both copies in step.

## Decided in this brainstorm (owner, 2026-11-09)

- **Hand-written schema plus conformance tests.** The schema is written by hand and tests keep it and the loader in agreement. It is not generated from the C# model, because the loader's rules live in a 1059-line hand-written reader that a generator cannot see.
- **Pack reference only.** Other docs-site pages that describe removed or outdated features are out of scope for this phase and are tracked in one issue.

## Goals

- A reference page with one entry per rule type: `forbid`, `allowOnly`, `require`, banned packages, unique names, and the `members` selector, each with fields, a short example, the violation kind it produces and its stated limits.
- `pack.schema.json` for schema 2, published on the docs site, with a short page on wiring it into VS Code, Rider and any editor that uses the YAML language server.
- Conformance tests that fail CI when the schema and the loader disagree.
- `docs/how-it-works/` and `docs/how-it-works.md` deleted, with `CLAUDE.md` and every live link updated.
- The deferred minor from 2.5: the awkwardly split `VacuousRule` message cell and its "Message starts with" column header on the rule-schema page.

## Non-goals

- Generating the schema or the docs from code.
- A schema for the settings file, the imports file or any non-pack YAML.
- Editing the other stale docs-site pages (code generation, git sync, orchestration, host applications, DI, and `Linter` mentions). One issue tracks them.
- `ariadne init` writing a `# yaml-language-server: $schema=` line into new packs. It touches the CLI and its tests, so it is a candidate for its own small change, not part of a docs phase.
- Submitting the schema to SchemaStore.
- A schema for v1 packs.

## Anti-goals

- A schema that accepts packs the loader rejects for a reason the schema could have caught, or one that rejects packs the loader accepts. Either one makes the editor lie.
- Two descriptions of the format that diverge silently. That is the failure the old `docs/how-it-works/` copy already showed.

## Constraints

- The loader stays the authority. JSON Schema cannot express cross-references (unknown layer names, duplicate ids, edits to locked rules, a child pack amending what it may not). The schema checks shape only, and the reference says which errors only the loader reports.
- The rule-schema page URL `/how-it-works/rule-schema` is linked from `src/Ariadne.NET.Abstractions/README.md` and must keep working.
- Shared VM: one build or test run at a time, no local AOT publish.
- The docs site builds with `npm run build` in `docs-site`; broken links fail that build.

## Approaches

1. **Hand-written schema plus conformance tests (chosen by the owner).** `pack.schema.json` by hand. Tests validate every built-in pack, this repo's pack and the fixture packs against it, and run a corpus of invalid packs through both schema and loader. Drift fails CI. Cost: a test-only dependency on a JSON Schema validator and a corpus to maintain.
2. **Generate from the C# model.** One source for shapes, but the strict-key walk, the role shorthand and the exception rules are in the reader, so the generated schema would be incomplete and need hand patches. Rejected.
3. **Hand-written, no enforcement.** Cheapest, and it drifts at the next rule type. Rejected.

## Design

### JSON Schema

- File `docs-site/static/schema/pack.schema.json`, draft 2020-12, `$id` set to its published URL on the GitHub Pages site. Docusaurus copies `static/` as is, so the URL needs no build step.
- Mirrors the loader's strictness: `additionalProperties: false` on every object, and the `schema` key is required and fixed to `2`.
- Each description string reuses the wording of the reference page, so editor hover text and docs say the same thing.
- It covers the full pack: top-level keys, `extends`, layers and retargets, `forbid`, `allowOnly`, `require`, selectors with `members`, exceptions, `bannedPackages`, `uniqueNames`, `componentRoles` and `allowEmpty`.

### Conformance tests

In `Ariadne.NET.Tests`:

- **Valid corpus:** every embedded built-in pack, `.architecture/rules.yaml` and each pack under `tests/fixtures` validates against the schema and loads through the loader.
- **Invalid corpus:** a directory of small invalid packs, each naming the one thing wrong (unknown key at each nesting level, wrong type, missing `schema`, `schema: 1`, missing `because`, bad enum value). Each is rejected by the schema and by the loader. The test fails if only one of them rejects it.
- **Known gap list:** cases the loader rejects and the schema cannot (unknown layer name, duplicate id) live in a separate list, asserted loader-only. This documents the limit and stops it growing unnoticed.
- YAML is converted to JSON for validation with the YAML library already in the repo, so no second YAML parser is added.

### Reference docs

- The rule-schema page keeps its URL and keeps the pack overview, top-level keys, layers, `extends`, load errors and the v1 migration section. The per-rule material moves out.
- A new sibling page, `rule-types`, holds the reference: one section per rule type with a fields table, an example, the violation kind and the limits already stated in the 2.3 to 2.5 designs. It sits directly after the rule-schema page in the sidebar.
- A section on editor support, on that page or a short page of its own, shows the `# yaml-language-server: $schema=<url>` line and the VS Code `yaml.schemas` setting, and says what the schema cannot check.

### Deleting the old copy

- Remove `docs/how-it-works/` and `docs/how-it-works.md`.
- Update `CLAUDE.md` so it no longer says the two copies exist. `docs/features.md` stays; it is not in the roadmap goal.
- Fix any live link to the deleted files. Historical design and plan documents keep their text as written.
- `docs.yml` already watches `docs/**` and `docs-site/**`; no workflow change.

## Left to the builder

- Which JSON Schema validator package to use for the tests; it must be test-only and compatible with draft 2020-12.

- Whether a reflection test that every public model property appears in the schema is worth its fragility; add it only if it stays simple.

## Risks

| Risk | Effect | Mitigation |
|---|---|---|
| The schema accepts something the loader rejects | An editor shows no error for a pack that fails to load | Invalid corpus runs through both; known gaps are listed and asserted |
| A new rule type lands without a schema change | Editor flags a valid pack | Valid corpus includes the repo's own pack and fixtures, and phase checklists name the schema |
| Splitting the rule-schema page breaks inbound links | Dead links from the README and published pages | Keep the page URL; docs build checks links |
| Stale pages left behind look current | Readers trust outdated pages | One tracking issue, linked from the phase completion note |
