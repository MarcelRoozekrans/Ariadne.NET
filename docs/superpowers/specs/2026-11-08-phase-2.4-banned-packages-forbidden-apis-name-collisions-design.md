# Phase 2.4 Design — Banned packages, forbidden APIs and name collisions

**Date:** 2026-11-08
**Phase:** `2.4`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-08

Milestone 2, Rule engine v2. Builds on `2026-11-04-milestone-2-design.md` and the 2.2 and 2.3 designs. Phases 2.1 to 2.3 are complete, so nothing here waits on an unfinished phase.

## Goal

A pack can ban packages from the resolved package graph of a project, confine individual APIs by member to chosen layers, and forbid a type name from being kept in two layers. The Daedalus appendix then has an expression for every row: the three banned-package tests, the one name-collision test, and the member-level reach that the security worked example in 2.6 needs.

## Intent and why

The appendix of the roadmap design maps 34 Daedalus architecture tests to rule types. After 2.3 three kinds are missing: banned packages (3 tests), cross-layer name collision (1 test), and member-level targets, which no Daedalus test needs but the milestone promises ("a pack can forbid namespaces, types and members per layer", with SQL, crypto and HTTP access confined to Infrastructure as the worked example). Milestone 4 replaces Daedalus's ArchUnitNET tests with an Ariadne pack, so these kinds have to be there first.

## Goals

1. A `bannedPackages` rule kind. A project whose resolved package graph, transitive packages included, holds a banned package is a violation.
2. A `members` selector key, usable on the `to` side of `forbid` and `allowOnly`, naming APIs at member level: methods, constructors, properties, fields and events.
3. A `uniqueNames` rule kind. A type in the `for` selector may not share its simple name with a type in the `against` selector.
4. Each violation carries the rule id and the `because`, as the 2.2 and 2.3 rules do, and CLI `rules`, MCP `get_rules`, CLI `validate` and MCP `validate_source` show the new kinds.
5. This repository's `.architecture/rules.yaml` gains one rule of each new kind as dogfood.

## Non-goals

- Vacuity detection and `allowEmpty`: phase 2.5. Until then a banned package that is absent, a member pattern that matches nothing and a `uniqueNames` rule that selects nothing are all silent.
- Package versions, version ranges and licences. A package is banned by id.
- The docs-site pack reference, the JSON Schema and the security worked example's final text: phase 2.6. This phase adds a short reference note per new key and no more.
- A dedicated built-in security pack. Layer names differ between packs, so none is planned (milestone design).
- Naming conventions stay with code generation.
- Module isolation stays in #32.

## Anti-goals

- A package check that passes because package information was missing. A run that cannot know the packages must say so and not report a clean result.
- A member rule that misses a call made through a subclass, which is the false negative a security rule cannot afford.
- Two matching implementations. Member patterns use the glob engine and the selector machinery of 2.2 and 2.3.
- A breaking change. This phase only adds values and keys.

## Constraints

- Globs are ordinal and case-sensitive for types, namespaces and members, as in 2.2. Package ids are the exception: they match case-insensitively, because NuGet ids are case-insensitive.
- Lists AND together and the values in a list OR, as in 2.2. A selector with no list matches every type, and the loader still rejects an empty selector.
- Generated code is not a rule subject, as in 2.1. It can still be a target.
- Only source types are checked as the source of a dependency.
- The strict loader rejects unknown keys. Every new key and rule kind needs a message in pack terms, with line and column.
- AOT-safe: the AotSmoke test stays in the verification of every task group. No reflection in `Ariadne.NET.Abstractions`.
- No performance regression beyond what the phase explains, measured against `docs/perf/phase-2.1-baseline.md` on this repository's own solution. The 2.2 note records the last accepted figures.
- No local AOT publish and one build or test at a time on the shared VM.

## Approaches

1. **One phase, three additions, built in the order name collisions, banned packages, member-level APIs (chosen).** All three add values to `RuleKind`, keys to the loader and violation kinds, so the shared plumbing is done once. The order puts the riskiest change, the reference walker, last. The cost is one larger PR; the plan keeps three task groups so each lands as its own commits.
2. **Split into 2.4a, 2.4b and 2.4c.** Smaller PRs, but three rounds of the same plumbing and a renumbering of 2.5 and 2.6 and everything that names them. Rejected.
3. **A generic "rules over graph facts" abstraction first.** Packages, members and names would all become facts the engine matches. Speculative with three different data sources and violation shapes, and it delays small things to build a large one. Rejected.

The owner chose approach 1 on 2026-11-08.

## Design

### Banned packages

```yaml
rules:
  - id: NO-FLUENTVALIDATION
    bannedPackages:
      packages: ["FluentValidation", "CSharpFunctionalExtensions", "ZeroAlloc.Scheduling"]
      from: { assemblies: ["Daedalus.Domain", "Daedalus.Application"] }
    because: Validation goes through ZeroAlloc.Validation.
```

- `packages` is a required, non-empty list of package-id globs, matched case-insensitively with the `*` and `**` rules of `types`. A glob like `Microsoft.EntityFrameworkCore*` bans a family.
- `from` is an optional selector. Only `assemblies` is meaningful, because a package belongs to a project and not to a type, and a project's assembly name is what the pack selectors already name. Any other key in `from` fails the load with a message that says why. Without `from` the rule covers every project.
- `exceptions` apply to a project, by assembly name, each with its own `because`, as on the other rules. On a `bannedPackages` rule an exception accepts `assemblies` only; `types` or `namespaces` there fail the load with a message that says a package belongs to a project. On a `uniqueNames` rule an exception accepts `types` and `namespaces`, which name `for` types, and rejects `assemblies` with a message that points to `from`-side selection through the rule's own `for` selector. `locked` and the 2.2 merge rules are unchanged.
- **Where the packages come from.** `Ariadne.NET.Workspaces` reads `obj/project.assets.json` of each project (the same file `ProjectCompiler` already checks for) and puts the resolved packages on `AnalyzedProject`. For a multi-targeting project each target framework has its own `targets` entry, and `AnalyzedProject` is already one entry per target framework, so each gets its own list. The file is NuGet's own resolved graph, direct and transitive packages with the dependency edges between them.
- **Model.** `AnalyzedProject` gains `IReadOnlyList<ResolvedPackage>? Packages { get; init; }`. `ResolvedPackage` holds the id, the version, whether it is a direct reference, and the shortest dependency path from a direct reference as a list of ids. `null` means the packages are not known, which is what an in-process caller that passes only a `Compilation` has.
- **Which packages count.** Every `type: package` entry in the project's `targets` counts, whatever its assets: analyzer, build-only and `PrivateAssets` packages are on the build's path too, which is the milestone's reason for counting transitive ones. Entries of `type: project` are not packages. A package that arrives only through a referenced project does count for the referencing project, and the path shows the project hop (`Daedalus.Domain references FluentValidation 11.9.0 through Daedalus.Shared`). The consequence is that every project on such a path reports the violation, and the path says which project holds the direct reference.
- **Direct.** `IsDirect` comes from the project's own `projectFileDependencyGroups` entry for the target framework, not from `targets`, which lists direct and transitive packages alike.
- **Unknown packages are an error, not a pass.** When a `bannedPackages` rule covers a project (after `from` is applied) and that project has `Packages == null`, `ArchitectureValidator.Validate` throws an `ArgumentException` that names the project, as `RejectMixedTargetFrameworks` does for its misuse. A project the rule does not cover, such as a test project with no assets file, is not checked and cannot trip the guard. In Workspaces a project with no assets file already fails the load with the existing restore hint, so the guard only matters to in-process callers, and no new error code is needed.
- **Violation.** One per rule, project and matching package. Kind `BannedPackage`, `SourceType` the project name, `Target` the package id, `Location` null. The message states direct or transitive and, for a transitive package, the path (`Daedalus.Domain references FluentValidation 11.9.0 through ZeroAlloc.Validation.Compat`). Identical violations across target frameworks are reported once, as for other violations.

### Member-level forbidden APIs

```yaml
rules:
  - id: SEC-SQL-ONLY-IN-INFRASTRUCTURE
    allowOnly:
      from: { layers: [Infrastructure] }
      to:   { members: ["System.Data.Common.DbCommand.Execute*", "Microsoft.Data.SqlClient.SqlCommand.*"] }
    because: Raw SQL stays behind the repositories.
  - id: SEC-NO-PROCESS-START
    forbid:
      from: { layers: [Domain, Application] }
      to:   { members: ["System.Diagnostics.Process.Start"] }
    because: Starting processes is an infrastructure concern.
```

- `members` is a list of globs over `Namespace.Type.Member`, using the glob rules of `types`: the segments up to the last dot name the type, the last segment names the member. `new` names a constructor (`System.Diagnostics.ProcessStartInfo.new`); `new` is a C# keyword, so it cannot clash with a member name, and a pattern never needs an empty segment. Nested types are written with dots between the type names, as `types` patterns already do (`Repo.Line.Close` for member `Close` of nested type `Line` in `Repo`). Properties are matched by their name (not their accessors), and events and fields likewise.
- `members` is accepted on the `to` selector of `forbid` and `allowOnly` only, and it combines with the other `to` keys by AND, as selector lists do. On `from` and on layer entries the loader rejects it with a message in pack terms, as it does for `types` on layers.
- **What counts as a use.** A call (including extension-method calls), a constructor call (`new T(...)`, target-typed `new(...)`, and the `: base(...)` and `: this(...)` initializers), a property or field read or write (an indexer is the property `Item`), an event subscription, and a method group conversion. Declaring a member is not a use. A `nameof` is not a use. Not recorded, as a stated limit of this phase: attribute constructors (the attribute class is still a type reference), implicit calls the compiler inserts (`foreach`, `using`, collection initializers, operators, deconstruction), and a member that is only the implementation of an interface member through a derived class (`class C : B, IFoo` where `B.Foo` satisfies `IFoo.Foo`, called as `c.Foo()`).
- **Override and implement matching (owner decision).** A use matches when the used member, or any member it overrides or implements, matches a pattern. Calling `SqlCommand.ExecuteReader()` matches a pattern that names `DbCommand.ExecuteReader`. An inherited member already binds to the declaring type, so only overrides and implementations need the walk up: `OverriddenMethod` and its relatives for overrides, and the interface members a member implements. The walk goes upwards only, so a call through an interface member does not match a pattern that names only the implementing class.
- **Generics.** Patterns match the original definition, without type arguments, so `System.Collections.Generic.List.Add` covers every `List<T>.Add`.
- **Walker.** `TypeReferenceWalker` already resolves a symbol for every name it visits. It records a member edge next to the type edge it records today: source type, the used member's symbol, location. The type edges stay as they are, so no type rule changes. Candidate names are checked before the chain is built, so only a use whose member name could match a pattern pays for the walk up.
- **Violations.** The existing kinds `ForbiddenDependency` and `DependencyNotPermitted` are reused. `Target` is the used member's display name, as `Namespace.Type.Member`, and the message names the pattern's member that matched when it is not the used one. Counting and locating work as for type edges: one violation per rule, source type and target with a reference count, located at the first use.
- **Open world.** As for types: `allowOnly` constrains only uses of members its `to` selector names. A member no pattern names is never a violation.
- **Members and type edges.** A `to` selector that holds `members` is evaluated on member uses only. A type reference with no member use, such as `typeof(SqlCommand)`, a field type or a declaration, is never a violation of such a rule. Other `to` keys in the same selector AND with `members` and are tested against the used member's containing type, so `to: { namespaces: ["Microsoft.Data.**"], members: ["**.SqlCommand.*"] }` matches a member of `SqlCommand` only if its declaring type is in that namespace. A `to` selector without `members` behaves exactly as today.
- **The candidate filter.** The walker first compares the used member's simple name with the member segment of every pattern, using the glob matcher, so a segment like `Execute*` filters correctly. An override or an implicit interface implementation keeps the name of the member it overrides or implements, so this filter loses no match. An explicit interface implementation is never a use by its own name, because code calls it through the interface member, which is what the use resolves to. A pattern whose member segment is `*` or `**` disables the filter for its type part, and the builder measures the cost.

### Name collisions

```yaml
rules:
  - id: WEB-KEEPS-NO-COPY-OF-DTOS
    uniqueNames:
      for:     { layers: [Web] }
      against: { namespaces: ["Daedalus.Application.**.Dtos"] }
    because: Web maps to its own view models and never copies an application DTO.
```

- `for` and `against` are selectors, both required and non-empty, and both accept every selector key including the 2.3 keys. They select source types.
- Two types collide when their simple names are equal: case-sensitive, namespace ignored, generic arity counted (`Result` and `Result<T>` differ). Nested types use their own name.
- **One-way (owner decision).** Each `for` type that shares a name with an `against` type is one violation, located at the `for` type, naming the other type in the message and in `Target`. A type in both selectors is not a collision with itself. If one type of the `for` set matches several `against` types, there is one violation per pair.
- **The check is solution-wide.** `for` and `against` types usually live in different projects, and the type graph is built per project. The check therefore runs after every project's graph is built, over their selected types, in the same step that holds `AddMissingInterfaceViolations`. It uses the one `LayerMap`, so a layer selector means the same thing in both sets. A type seen in several target frameworks of one project counts once.
- `exceptions` name `for` types (by `types` or `namespaces`) that may keep a colliding name, each with a `because`. `locked` and the merge rules are unchanged.
- Kind `NameCollision`.

### Rule kinds, keys and the loader

- `RuleKind` gains `BannedPackages = 4` and `UniqueNames = 5`. `RuleDefinition` gains a package list for the first and an `Against` selector for the second, the same way `Require` carries `RuleRequirement`; the exact shape is the builder's. `TargetSelector` gains `Members`. `ViolationKind` gains `BannedPackage = 9` and `NameCollision = 10`.
- The YAML reader recognises the keys `bannedPackages` (with `packages` and `from`), `uniqueNames` (with `for` and `against`) and `members`. Each rule body holds exactly one of `forbid`, `allowOnly`, `require`, `bannedPackages`, `uniqueNames`, as 2.3 enforces for the first three.
- Reserved ids stay as in 2.3. No new reserved prefix.
- Rule merging for a child pack is the 2.2 behaviour. The new kinds are ordinary rules: a child adds them and adds exceptions to unlocked ones.

### Where it lives

- **Abstractions** (additive): `RuleKind`, `RuleDefinition`, `TargetSelector`, the `ResolvedPackage` shape if it sits here, and `Members` in the validators. No `feat!`.
- **Engine** (`Ariadne.NET/Analysis`): `AnalyzedProject.Packages`; a `BannedPackageRules` checker and a `UniqueNameRules` checker beside `ForbidRules`; member edges in `TypeGraph` and the walker; `TargetMatcher` learns `members`; `ViolationKind` values; the null-package check in `ArchitectureValidator`.
- **Workspaces:** reading `project.assets.json` into `ResolvedPackage` in `ProjectCompiler` or a neighbouring class.
- **Loader:** `PackYamlReader` keys and messages; the merger.
- **Surfaces:** CLI `rules` and MCP `get_rules` list the new kinds and the `members` key; `validate` and `validate_source` report the new violation kinds.
- **Docs:** one short reference note per new key on the rule-schema page. The full reference and the security worked example are 2.6.
- **Dogfood:** `.architecture/rules.yaml` gets a `uniqueNames` rule, a `bannedPackages` rule for a package this repo already avoids (the builder picks one that is a real convention, and checks it against the lock files) and a `members` rule. The ten built-in packs gain none, as in 2.3.

## Tests

- **Unit, per kind.** Banned packages: direct, transitive with a path, glob family, case-insensitive id, `from` scoping, exceptions, multi-target dedupe, `Packages == null` throws. Members: call, constructor, property and field access, event subscription, method group, extension method, generic original definition, override and implement chains, a call through an interface member, a declaration that is not a use, `forbid` and `allowOnly`. Name collisions: one-way direction, arity, a type in both sets, several matches, cross-project, exceptions.
- **Loader:** each new key, each rejection (`members` on `from`, `from` keys other than `assemblies`, empty lists, two rule bodies in one rule), line and column.
- **Workspaces integration:** a fixture solution that has a restored transitive package, with a clean and a broken variant. The Daedalus-shaped fixture of 2.3 gains the three banned-package rows and the collision row.
- **Allocation and AOT:** the allocation tests stay green, the walker change is measured against the 2.1 baseline, and AotSmoke runs in CI as before.
- **Dogfood:** this repository passes its own pack in CI. Each dogfood rule must name something real in this repository, so that 2.5's vacuity check does not flag it, and each is backed by a positive test case in a fixture that shows it fires. A rule that is vacuous here, or has no positive test, does not count.

## Open Questions

None that block the plan. The calls below are mine, for review:

- Package ids match case-insensitively; every other glob stays case-sensitive.
- `bannedPackages` scopes by `from: { assemblies }` only.
- Unknown packages in a project that a banned-packages rule covers throw `ArgumentException` for in-process callers; uncovered projects are not checked.
- Every `type: package` target entry counts, analyzers and build-only packages included, and a package that arrives through a referenced project counts for the referencing project, with the project hop in the path.
- Exceptions on a `bannedPackages` rule take `assemblies` only; on a `uniqueNames` rule they take `types` and `namespaces` only; other keys fail the load.
- A `to` selector with `members` is evaluated on member uses only, and its other keys test the used member's containing type.
- The dogfood rules must be non-vacuous in this repository and each has a positive test.
- `ForbiddenDependency` and `DependencyNotPermitted` are reused for member violations; only `BannedPackage` and `NameCollision` are new kinds.
- Member patterns match the original definition; the override walk goes upwards only.
- `uniqueNames` runs once over all projects and not per project.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Member edges slow the walker or allocate per name | The check regresses beyond the 2.2 figures | Build the override chain only for a use whose member name can match a pattern; measure against the 2.1 baseline in the first task that touches the walker |
| `project.assets.json` differs between SDK versions or layouts | Packages are misread or the file is not found | Reuse the lookup `HasAssetsFile` already does; read only `targets` and `libraries`; test against the fixture solutions on the SDK the CI uses |
| A transitive path is wrong or very long | The message misleads | Use the shortest path from a direct reference; cap the printed path and say so |
| `Members` matches too widely or too narrowly because of display-name rules (nested types, extension blocks, explicit interface implementations) | Rules miss uses or flag the wrong ones | Normalise names in one place beside `TypeNames`, with a test per case in the list above |
| Name collision across projects gets slow on large solutions | A quadratic comparison | Index the `against` names in a dictionary once per run |
| The null-package guard breaks an existing in-process caller | A pack with a `bannedPackages` rule fails for a caller that passes only a `Compilation` | Only packs that hold the rule are affected, and none do today; the error names the project and the fix |

## Left to the builder

The exact types and names of the model additions; the diagnostic wording; the `project.assets.json` parsing details; how member edges are stored in `TypeGraph`; which package the dogfood rule bans; test fixture layout. The plan names the commits that touch the public API, and there is no breaking change to mark.
