# Issue #127: check Razor component code — design

**Status:** approved by the owner 2026-11-14. A small change: short design.

## Intent

A `.razor` file's markup and `@code` block reach the compilation only as output of the Razor source generator. Ariadne skips
every generator tree (`ProjectCompiler` puts them in `GeneratedTrees`, `TypeGraphBuilder` skips them through
`GeneratedCode.IsGeneratedTree`), so no rule sees component code. Daedalus PR #456 proved it: a `@code` block that used an
Infrastructure type and declared a `ProjectDto` copy passed the pack, where the ArchUnitNET tests it replaces, which read the
compiled assembly, failed. #456 waits for this fix.

## Goals, non-goals

- Goal: trees from the Razor source generator are checked as hand-written source, by every rule kind.
- Goal: a violation in such a tree points at the `.razor` file, through its `#line` mapping.
- Non-goal: any other generator. Their output stays skipped.
- Non-goal: a pack schema change, or a switch to turn this off.
- Anti-goal: recognising Razor trees by file name (`*_razor.g.cs`); they are recognised by their generator.

## Facts measured 2026-11-14 on Roslyn 5.12 and SDK 11.0.100

- `SourceGeneratedDocument` has no public member naming its generator; `SourceGeneratorIdentity` is internal. The workspace
  builds the document's `FilePath` from that identity: `<intermediate>/<generator assembly name>/<generator type full name>/<hint name>`,
  for example `obj/Debug/net10.0/Microsoft.CodeAnalysis.Razor.Compiler/Microsoft.NET.Sdk.Razor.SourceGenerators.RazorSourceGenerator/Components/Counter_razor.g.cs`.
- On SDK 11 one component gives two trees: `Counter_razor.g.cs` (markup, `BuildRenderTree`) and `Counter_razor.decl.g.cs`
  (the `@code` members). Both come from the same generator.
- `#line` maps the user's expressions and `@code` block to the `.razor` file (`GetMappedLineSpan` gives `HasMappedPath` true).
  Razor's boilerplate, such as the class declaration and the `ComponentBase` base type, sits under `#line hidden` and maps to
  the generated file. `Counter_razor.g.cs` starts with `#pragma checksum "<path of the .razor file>"`; the `.decl.g.cs` tree has no pragma.

## Approaches

1. **Generator-type segment of the generated document's path (chosen).** In `ProjectCompiler`, a generated document whose
   path has the folder `Microsoft.NET.Sdk.Razor.SourceGenerators.RazorSourceGenerator` directly above its hint name is a Razor
   tree. This is the generator identity as Roslyn writes it; the type name is the same on every SDK, while the assembly
   segment changed between SDKs, so only the type segment is matched. Cheap, public API only.
2. Re-running the generators with a `GeneratorDriver` to read `GeneratorRunResult.Generator`: doubles generator time and needs
   the project's additional files and analyzer options rebuilt by hand. Rejected.
3. Reading the internal `SourceGeneratedDocument.Identity` by reflection: breaks silently on a Roslyn update. Rejected.

## Design

- `AnalyzedProject` gains `RazorTrees` (`IReadOnlySet<SyntaxTree>`, empty by default). `GeneratedTrees` holds the generator
  trees that stay skipped, so it no longer holds Razor trees.
- `GeneratedCode.IsGeneratedTree` takes the Razor set and returns false for a tree in it before any other check, since Razor
  trees carry `<auto-generated/>` and a `.g.cs` name.
- The whole Razor tree is walked, not only its mapped spans: the component is a source type (`uniqueNames`, `require`,
  layers), and component tags in markup, `@inherits` and the default `ComponentBase` count as dependencies, as they do for
  ArchUnitNET, which reads the assembly.
- Locations in a Razor tree: the mapped `.razor` position when the span maps; otherwise line 1, column 1 of the `.razor`
  file, whose path comes from the tree's first mapped `#line` directive, else its `#pragma checksum`; the generated path only
  when the tree names no file at all. Trees outside the Razor set keep their unmapped location.
- Consequences, accepted: `_Imports` classes and `.cshtml` views (namespace `AspNetCoreGeneratedDocument`) become source types too.
- The parity catalogue lists ArchUnitNET API rows only, so it gets no row for this.

## Tests

Test first on `tests/fixtures/razor`: a component whose `@code` crosses a forbidden layer and declares a type a `uniqueNames`
rule catches, both reported at the `.razor` file. Loader tests: Razor trees land in `RazorTrees`, not in `GeneratedTrees`;
another generator's output (`tests/fixtures/generator`) stays in `GeneratedTrees`. Unit tests for the location fallback.

## Left to the builder

Names of helpers, where the Razor-path lookup lives, and how the fixture's pack is written.
