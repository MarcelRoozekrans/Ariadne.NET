## Goal

Two GitHub Actions examples show a build failing on a violation (one with the tool and SARIF code scanning, one with `dotnet test`), a docs page explains them, and this repo's CI proves the failing exit code on a broken fixture.

## Approach

**Examples.** `examples/github-actions/` holds two complete workflow files users copy:

- `ariadne-tool.yml`: checkout, `setup-dotnet`, `dotnet restore` (the packages-banned rule needs `obj/project.assets.json`), `dotnet tool install --global Ariadne.NET.Cli`, `ariadne validate <solution> --format sarif --output ariadne.sarif` and, with `if: always()`, `github/codeql-action/upload-sarif` with `sarif_file: ariadne.sarif`. The validate step is the one that fails the job (exit 1 on violations, 2 when it cannot run). The workflow sets `permissions: security-events: write` for the upload and `contents: read`. A comment says the upload needs code scanning to be available for the repository.
- `ariadne-test.yml`: checkout, `setup-dotnet`, `dotnet test`; the test project calls `ArchitectureCheck.AssertValid()` (shown in the docs page, not in the workflow). A violation is a failing test, so `dotnet test` fails the job.

Pinned action versions follow what `ci.yml` uses today (`actions/checkout@v7`, `actions/setup-dotnet@v6`); the CodeQL action is pinned to the major the repo's `baseline-checks.yml` uses.

**The proof job.** A new `ci.yml` job `fail-the-build` (`needs: pack-validate`, ubuntu) proves the claim the examples make. `pack-validate` uploads `artifacts/packages` as a one-day artifact; the new job downloads it, installs the tool with `--tool-path` from that folder, restores `tests/fixtures/broken`, and runs exactly the command line of the example: `ariadne validate tests/fixtures/broken --format sarif --output "$RUNNER_TEMP/ariadne.sarif"`. It asserts exit code exactly 1 (so a crash, 2, fails the job), that the SARIF file exists and its first result has a `ruleId` and a `level` of `error`, and that the same command on `tests/fixtures/clean` exits 0. A unit test also parses the example workflow files so the proof and the example cannot drift: it asserts that each example contains the install line, the validate line with `--format sarif --output`, and that the proof job in `ci.yml` uses the same validate flags.

**Fixture packs.** `tests/fixtures/broken` and `tests/fixtures/clean` have no `.architecture` folder, and discovery walks up, so they would find this repository's own pack. Each gets its own `.architecture/rules.yaml` (schema 2) that fits it: `broken` reports a violation, `clean` none. Existing tests that load these fixtures pass explicit packs and are not affected; a new Workspaces test pins that `IPackSetValidator` on each finds its own folder.

**Docs.** A docs-site page `ci-github-actions.md` (placed next to the other how-to pages and added to the sidebar if it is not automatic) explains both examples, the exit codes, restoring first, where violations show in code scanning, the `ArchitectureCheck` snippet for xUnit, NUnit and MSTest, and links to the report formats page. The docs site's `docs.yml` build must pass.

## Tests

- Unit: the example workflow test (install line, validate flags, permissions, `if: always()` on the upload); a test that every YAML file under `examples/github-actions` parses.
- Integration: `IPackSetValidator` on `broken` gives at least one violation and on `clean` none, each with its own `.architecture` folder discovered (not the repo's).
- CI: the `fail-the-build` job. Locally the same command line is run once against a tool packed into a temp folder with `--tool-path`, never global.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The fixture pack matches nothing and the vacuity check fails it | The proof fails for the wrong reason | The fixture packs are written from the fixture's own namespaces and tested in the Workspaces test |
| The examples drift from the proof job | The docs promise something CI no longer checks | The example workflow test compares the flags |
| Code scanning is unavailable for private repositories without Advanced Security | A user's upload step fails | The docs page says so; the upload is the last step and the validate step has already failed or passed |
| `actionlint` false positives on the examples | Noise | Only the two known `create-github-app-token` ones are ignored; the examples do not use that action |
