## Goal

The CLI and the testing package write the same JSON and SARIF 2.1.0 reports; a test validates the SARIF against the published schema.

## Approach

**Writers in the engine.** Two public static writers in `Ariadne.NET` (`Reports/`), beside `TextReportWriter`: `JsonReportWriter.Write(Stream output, ArchitectureReport report, ReportContext context)` and `SarifReportWriter.Write(...)` with the same shape. `ReportContext` is a small record: `Root` (the folder paths are made relative to) and `ToolVersion`. Output is UTF-8 without a BOM.

**JSON** is Ariadne's own and versioned: `{"schema":1,"tool":{"name":"ariadne","version":"…"},"typesChecked":n,"projects":[…],"skippedProjects":[…],"violations":[{"ruleId","pack","kind","sourceType","message","because","target","location":{"path","line","column"},"referenceCount","targetFrameworks"}]}`. Paths are relative to `Root` with `/` separators; a violation without a location omits `location`. Property names are camelCase and the order is fixed so output is stable and diffable.

**SARIF 2.1.0**: one run, `tool.driver` with name `Ariadne.NET`, version, `informationUri` (the docs site), one `reportingDescriptor` per distinct rule id seen (`id`, `shortDescription` the first message kind, `help.text` the `because`, and `properties.pack`). One `result` per violation with `ruleId`, `level` `error`, `message.text`, one `location` with a `physicalLocation` whose `artifactLocation` has `uri` relative to the root and `uriBaseId` `%SRCROOT%`, and `region` `startLine` and `startColumn`; a violation without a location gets a `logicalLocation` of the source type instead. The run carries `originalUriBaseIds` with `%SRCROOT%` set to the root as a `file://` URI. `properties.pack` and `properties.targetFrameworks` on each result carry the extras. Two packs that define the same rule id produce two descriptors (`id` stays the rule id, `properties.pack` differs) and results point to the one that matches their pack by `ruleIndex`.

**Root.** The repository root for relative paths is the nearest ancestor of the solution folder with a `.git` entry (file or folder), else the solution folder. A small public helper `ReportRoot.Find(string solutionFolder)` in `Ariadne.NET` does this; both hosts use it.

**Serializer spike.** The roadmap names ZeroAlloc.Serialisation for the writers. Task 1 spikes whether it can write these shapes without reflection and stays AOT-friendly. If it can, the writers use it. If it cannot (SARIF needs nested optional objects and dictionaries), the writers use `Utf8JsonWriter` and the outcome and reason are recorded in this design under "Spike outcome". Either way the public writers and the tests are the same.

**CLI.** `validate [path] --format text|json|sarif` (default `text`) and `--output <file>`. With `--output` unset, JSON and SARIF go to stdout and the summary lines (`Checked n types…`, the `Result:` line) go to stderr so stdout stays parseable; text goes to stdout as today. With `--output`, the file holds the report and the text summary stays on stdout. An unknown format is a usage error. The output file's folder is created if missing; a write failure is exit 2. Exit codes do not change.

**Testing package.** `ArchitectureCheck.WriteReport(ArchitectureReport report, ReportFormat format, string path)` writes a report to a file, with `ReportFormat` an enum `Json`, `Sarif`. It uses `ReportRoot.Find` on the solution's folder, which `ArchitectureCheck` knows. `AssertValid` gets an optional `string? reportPath` and `ReportFormat? format` so a test can write SARIF and still fail; the file is written before the exception is thrown.

**SARIF validation.** The SARIF 2.1.0 JSON schema from the OASIS spec repository is vendored under `tests/Ariadne.NET.Tests/Reports/` with its source URL and date in a README beside it. A test-only JSON Schema package (`JsonSchema.Net`) validates real output (the `twopacks` report, a report with no violations, a report with a violation without a location) against it. No network at test time.

## Tests

- Unit: JSON golden file for the `twopacks` report and for an empty report; SARIF golden files for the same; relative paths with a nested project; a violation without a location; the same rule id from two packs gives two descriptors; unknown or missing `because` gives an empty help text; `ReportRoot` finds `.git` as a folder and as a file and falls back to the solution folder.
- Schema: the SARIF output validates against the vendored 2.1.0 schema in all three cases.
- CLI: `--format json` puts parseable JSON alone on stdout and the summary on stderr; `--format sarif --output x.sarif` writes the file and exits 1 on `twopacks`; an unknown format is a usage error; exit codes unchanged for all formats.
- Testing package: `WriteReport` writes both formats; `AssertValid` with a report path writes the file and still throws.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| ZeroAlloc.Serialisation cannot express the shape | The writer needs another library | Task 1 spike; fall back to `Utf8JsonWriter`, recorded here |
| The SARIF schema cannot be downloaded in the run | The schema test cannot be written | The task says so and parks; the owner supplies the file. No other source is acceptable |
| Absolute paths leak into SARIF | Code scanning shows no locations | Paths are relative; the nested project test covers it |
| stdout carries summary text with `--format json` | A consumer cannot parse stdout | The summary goes to stderr in that mode; a CLI test parses stdout |
