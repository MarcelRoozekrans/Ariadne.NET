**Date:** 2026-11-11
**Phase:** 4.4
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-11

## Goal

A `forbid`, `allowOnly` or `uniqueNames` rule can set `requireTarget: true`, and then fails as `VacuousRule` when its target selector matches nothing the loaded solution uses: for `forbid` and `allowOnly`, no type it declares or references, or no member edge when the target names `members`; for `uniqueNames`, no type it declares, because `uniqueNames` compares declared types only.

## Why

Phase 2.5's vacuity check looks at a rule's subject only. A rule whose target matches nothing passes quietly. If Thalos renames `ISubagentRunner`, Daedalus's single-seam `allowOnly` rule to `Thalos.ISubagentRunner` keeps passing while it checks nothing. In ArchUnitNET, Daedalus guards this with C# facts: `SubagentRunnerType_IsLoaded_…`, the `…Assembly_IsLoaded_…` facts, `AgentsProject_DoesDependOn_Thalos_RulesAreLoadBearing`, `MemoryRagNetAdapter_DoesDependOn_RagNet_RuleIsLoadBearing` and `ApplicationDtoNames_CoverEveryDtoNamespace_…`. The migration guide must map those facts to something Ariadne checks, not to "not needed". CodeRabbit raised this on PR #84.

## Decisions

Taken with the owner on 2026-11-11:

- **Target vacuity is part of Milestone 4.** It is a phase of its own, before the migration guide, so the guide can map the load-bearing facts to it. The guide becomes 4.5 and the Daedalus switch-over 4.6.
- **Opt-in per rule.** A rule sets `requireTarget: true`. Nothing is on by default, because a preventive rule such as "forbid Newtonsoft", which nobody references on purpose, has an empty target by design. Nothing in this phase is breaking.
- **"Found" means declared or referenced.** A target is found when it matches a source type or an edge target of any graph in the run, the same universe `VacuityRules` already uses to find layers. This catches a rename and also proves that something in the solution uses the target, which is what the Daedalus facts check.

## Approaches considered

- **A — Declared or referenced, opt-in per rule (chosen).** Cheap: the graphs already hold every source type and edge target. It matches layer vacuity.
- **B — Exists in any loaded assembly.** Found when any type in the compilations or their referenced assemblies matches, used or not. It catches renames only, and walking every referenced assembly costs time per target framework. Rejected.
- **C — A separate `exists` rule kind,** written next to the rule it guards. It leaves `forbid` and `allowOnly` unchanged but costs more YAML, and the guard can drift from the rule it protects. Rejected.
- **On by default with `allowEmptyTarget`,** mirroring 2.5. Breaking for every preventive rule in user packs. Rejected by the owner.

## Approach

### Model and loader

- `RuleDefinition` gains `bool RequireTarget`, default `false`. YAML key `requireTarget`, a strict boolean.
- `PackYamlReader` accepts `requireTarget` on a rule whose kind is `forbid`, `allowOnly` or `uniqueNames`. On a `require`, `bannedPackages` or, after 4.3, `slices` rule it is a load error at the key's location: `'requireTarget' applies only to forbid, allowOnly and uniqueNames rules`. `RuleDefinitionValidator` holds the same rule as a `Must` backstop for packs built in code.
- A child pack cannot set it on an inherited rule: an amendment still carries only `id` and `exceptions`. `RulePackMerger` copies the field with the rule.
- `RulePackDescriber` adds `requireTarget` to a rule's description when it is set.

### The check

`VacuityRules.CheckRules` gains a second pass per rule with `RequireTarget`. It runs whatever the subject check found and whatever `allowEmpty` says, because `allowEmpty` is about the subject only.

- **`forbid` and `allowOnly`:** the target is `to`, compiled with `TargetMatcher.From(rule.To, map)`, as `DependencyRuleChecker` compiles it. It is found when it matches a source type or an edge target of any graph. When `to` has `members`, it is found when a member edge of any graph matches it as `DependencyRuleChecker` matches a member reference. `MemberNameFilter` already lets every rule's member patterns through, so the edges are there.
- **`uniqueNames`:** the target is `against`, found when it matches a source type of any graph, as `UniqueNameRules.Collect` reads it.
- **`to` with only `layers`:** found when a source type or edge target lies in one of the layers, through the same matcher. When every named layer is already reported as `VacuousLayer`, the target check is skipped, as the subject check skips a rule whose `from` names only vacuous layers.

A target that is not found gives one violation, after the rule's subject violation if there is one: `Kind = VacuousRule`, `RuleId` and `SourceType` the rule id, `Because` the rule's `because`, no location, and the message `Rule '<id>' requires its target, but its 'to' selector matches no type declared or referenced in the <n> project(s) loaded.` For `uniqueNames` it reads `Rule '<id>' requires its target, but its 'against' selector matches no type declared in the <n> project(s) loaded.` For a `to` that names `members` it reads `Rule '<id>' requires its target, but no code in the <n> project(s) loaded uses a member its 'to' selector names.`, because the type may well exist while the member is unused.

### Docs and schema

- `rule-types.md`: the Vacuity section explains `requireTarget`, when to set it (the target is a real seam, a type the solution uses), and when not (a preventive `forbid` of a library nobody uses), with the Thalos example.
- `03-rule-schema.md`: the rule keys table gains `requireTarget`.
- `docs-site/static/schema/pack.schema.json`: `requireTarget` is a boolean on the rule. "Only on forbid, allowOnly and uniqueNames" goes into `ShapeGaps` if the schema cannot express it, as other kind-dependent keys do.
- `tests/Ariadne.NET.Tests/PackSchema`: a valid case with `requireTarget` on each of the three kinds, and invalid cases for a non-boolean value and for `requireTarget` on `require`.

### What the guide and Daedalus get

The 4.5 guide's test map maps `…IsLoaded…`, `…DoesDependOn…RulesAreLoadBearing` and `ApplicationDtoNames_Cover…` to the pack rules whose target each fact guards, with `requireTarget: true` on those rules, but only where Daedalus code itself declares or references the target. `MemoryRagNetAdapter_DoesDependOn_RagNet_RuleIsLoadBearing` is the exception: its own comment says nothing in the solution references Rag.NET directly, so `requireTarget` on the Rag.NET rule could never be satisfied; that fact stays in C#, rewritten as a reflection check that a Rag.NET type such as `IVectorStore` still lives under the `Rag.` namespace.

`requireTarget` proves that a target resolves to something the solution uses. It does not say which project uses it, so it does not reproduce "Daedalus.Agents depends on Thalos" as such. The Daedalus facts' comments give their purpose as "the pattern must resolve to real Thalos types", which is what `requireTarget` checks; and because the pack's `forbid` rules already flag every other layer that references Thalos, a found Thalos target can only come from Agents or a host no rule restricts. 4.6 ships that pack. `AgentsProject_DoesDependOn_Thalos_RulesAreLoadBearing` guards the Thalos `forbid` rules, the `ZeroAllocOrm`, `ZeroAllocOutbox` and `Cronos` `IsLoaded` facts guard the Domain `forbid` rules, `SubagentRunnerType_IsLoaded` guards the single-seam `allowOnly`, and `ApplicationDtoNames_Cover…` guards the `uniqueNames` rule. The `SkillsAssembly_IsLoaded…` and `ChannelsAssemblies_AreLoaded…` facts are `not needed`: they make ArchUnitNET load two Thalos assemblies so the `Thalos` pattern sees their types, and Ariadne reads every referenced assembly through the compilation; the pattern's resolution is the Thalos rules' own `requireTarget`, and no rule targets the Skills or Channels namespaces on their own. `ApplicationDtoNames_Cover…` checks that the C# helper `ApplicationDtoNames()` reads the DTO root namespace and its sub-namespaces; the helper goes with the switch, and the pack's `against` is `Daedalus.Application.DTOs.**`, which covers both because `**` matches zero or more segments. 4.6's red checks copy one root and one nested DTO into Web, so narrowing the selector is caught.

## Tests

- **Unit, vacuity:** a `forbid` with `requireTarget` whose `to` matches an edge target from another project is not reported; the same rule after the target is renamed is reported with the exact message; a target matching only a source type, with no edge to it, is found; `to` with `members` is found through a member edge and reported without one; `uniqueNames` `against` matching nothing is reported with `'against'` in the message; `allowEmpty: true` with an empty subject and an empty target gives only the target violation; a rule without `requireTarget` and an empty target gives nothing; `to: { layers: [L] }` with `L` vacuous gives only the `VacuousLayer`.
- **Unit, loader and validator:** the key parses on the three kinds; it is a located error on `require` and `bannedPackages`, and on a non-boolean value; the validator rejects a code-built `require` rule with `RequireTarget = true`.
- **Schema conformance:** the valid and invalid cases above.
- **Regression:** the whole solution and the repo's own `ariadne validate` stay green; no shipped pack sets the key.

## Calls made while writing this up

Settled by Claude, not discussed; correct any of them.

- The key is named `requireTarget`, next to `allowEmpty`.
- `allowOnly` gets the same opt-in as `forbid`, not a different default.
- `bannedPackages` and `slices` get no target check: a banned package nobody references is the normal state, and a slices rule's `allow` is an exemption, not a target.
- The violation reuses `VacuousRule` (11) instead of a new kind, so reports, SARIF and the vacuity docs need no new kind.
- The subject and the target check are independent, so a rule with both problems gets two violations with different messages.
- The phase does not touch this repo's own pack or the built-in packs.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A `to` with `members` matches no member edge because `MemberNameFilter` dropped the member names | The target reads as not found, a false violation | `MemberNameFilter` already reads every rule's `To.Members` (checked at `26d5725`). The plan's vacuity tests pin a member target found through a member edge. |
| 4.2 and 4.3 also change `PackYamlReader`, the schema and `VacuityRules` | Merge conflicts in an unattended stacked run | This phase runs after 4.3 on top of its branch; the plan names the key sets as 4.3 leaves them. |
