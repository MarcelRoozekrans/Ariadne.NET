## Goal

One call in a test checks every pack under `.architecture/` against the solution and fails with each broken rule's id, pack and `because`; `ariadne validate`, the stop hook and MCP validation check the same packs.

## Correction to the milestone design

The milestone design says a pack in `.architecture/` that a sibling imports is a base, "covered by" the importer. That rests on a wrong reading of `PackOperations.LoadReference`: `extends` accepts only `builtin://` and `import://`, and `import://<name>` loads from `.architecture/.cache/git/<name>/`, filled by `ariadne sync`. A pack file in `.architecture/` can never be imported by a sibling, so there is no base-pack case. This phase drops that call: every `*.yaml` or `*.yml` directly in `.architecture/` is a pack that is checked on its own. The `.cache` folder is a subfolder and is never scanned, because discovery is non-recursive.

## Approach

**Shared engine pieces.** `ArchitectureViolation` gets `string Pack { get; init; } = ""` (not `required`, so it is a plain `feat`). A public `TextReportWriter` in `Ariadne.NET` (`Reports/`) takes over the text rendering that `ValidateCommand.Print` does today, plus the pack name per violation, so the CLI and the testing package print the same text. `Print` then calls it. The single-pack `SolutionValidator.ValidateAsync` stamps `Pack` from the resolved pack's `Name` on every violation it returns.

**Multi-pack check in Workspaces.** A new public `IPackSetValidator` with `Task<Result<ArchitectureReport, AriadneError>> ValidateAsync(string path, CancellationToken)` does the whole job from a solution path:

1. `PackDiscovery` resolves `path` with `SolutionPath`, starts in the solution's folder and walks up to the first ancestor with an `.architecture` folder, and lists `*.yaml` and `*.yml` directly in it, sorted by file name with ordinal comparison. No folder, or no file, is `NotFound`. The folder that holds `.architecture` is the working directory handed to the resolver, so `import://` finds `.architecture/.cache`.
2. Each file is loaded with `IRulePackLoader.LoadFromFile` and resolved with `IRulePackResolver.Resolve(pack, workingDirectory)`. The first failure fails the whole check; its message is prefixed with the file name so the user knows which pack broke. Two files with the same pack `name` are an `Invalid` error naming both files.
3. The solution is loaded once. The existing `SolutionValidator` loads and validates per pack, so this phase splits it: a new internal step takes a `LoadedSolution` and a pack, and both `SolutionValidator` and the pack-set validator use it. This avoids loading MSBuild once per pack and keeps `FindPackageCoverageGap` per pack (a `bannedPackages` rule in any pack that cannot see the package list fails the check).
4. Violations are merged in pack order into one `ArchitectureReport` (projects and types checked from the first run; skipped projects once). Types checked is the solution's count, not summed per pack.

`IPackSetValidator` is registered in `AddAriadneNETWorkspaces()`.

**Hosts.** CLI `validate` stops calling `ResolveRulesFromFile` and calls `IPackSetValidator`; `ResolveRulesFromFile` stays for `rules` and `roles`. `StopHook` calls `IPackSetValidator` with the solution `SolutionDiscovery` finds (a `NotFound` still skips silently, as `IProjectRules.Load` does today); `IProjectRules` stays for session-start and pre-tool-use. MCP `validate_source` with an explicit `template` keeps the single-pack path; without one it calls `IPackSetValidator`, and when that finds no `.architecture` it falls back to the `clean-architecture` default exactly as today, so existing MCP behaviour for projects without packs does not change.

**The package.** `Ariadne.NET.Testing` is a new packable net10 project that references `Ariadne.NET.Workspaces`. API, framework-agnostic and static:

- `ArchitectureCheck.Run(string? solutionPath = null)` returns the merged `ArchitectureReport`, or throws `ArchitectureCheckException` when the check could not run (no packs, bad pack, no solution, load failure), with the error message and detail.
- `ArchitectureCheck.AssertValid(string? solutionPath = null)` throws `ArchitectureViolationException` whose `Message` is the text report when there are violations. It is also an `ArchitectureCheckException` subtype so test code can catch one type.
- With no `solutionPath` the solution is the single `.sln` or `.slnx` found by walking up from `AppContext.BaseDirectory`; more than one in the nearest folder that has any is an error naming them.
- The call is synchronous (it blocks on the async validator) because test frameworks differ on async test support. `RunAsync` and `AssertValidAsync` overloads sit beside them.

MSBuild reference. Every project that references Workspaces adds `Microsoft.Build.Framework` with `ExcludeAssets="runtime"`, or the build fails with `MSBL001`. Task 1 of the plan is a spike: pack `Ariadne.NET.Testing` with a `buildTransitive/Ariadne.NET.Testing.props` that adds that reference to the consumer. If MSBuild or NuGet rules prevent it, the package instead fails at first call with a message that names the exact `PackageReference` line, the README and docs page state the line, and the Definition of Done item reads "one call plus that documented line". The spike's outcome is recorded in this design under a new heading before the rest of the package is written.

## Tests

- Unit: `Pack` stamped by the single-pack path; discovery order, walk-up, non-recursion, `.yml` accepted, `.cache` ignored, missing folder and empty folder both `NotFound`; duplicate pack name; first failing pack fails the check and names the file.
- Integration: `twopacks` gives exactly the broken pack's violations with the pack name and `because`; the clean pack alone passes; a `bannedPackages` coverage gap in the second pack fails the check; the solution loads once (a counting `ISolutionLoader` stub).
- Testing package: `AssertValid` passes on `clean`, throws `ArchitectureViolationException` on `twopacks` with the text containing rule id, pack and `because`; `Run` returns the report; no solution found, two solutions in the nearest folder and no packs each throw `ArchitectureCheckException`; a test in `Ariadne.NET.Testing.Tests` calls it from its own output folder to prove the walk-up from `AppContext.BaseDirectory` finds this repo's solution and `.architecture/rules.yaml`.
- Hosts: `validate` on `twopacks` prints the pack per violation and exits 1; the stop hook and `validate_source` report the same violations as the CLI for `twopacks`.
- Package: `pack-validate` inspection accepts the fourth package.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A fixture without its own `.architecture` finds this repo's pack by the walk-up | A fixture test passes or fails for the wrong pack | Every fixture used with `IPackSetValidator` carries its own `.architecture`; `twopacks` does, and a test asserts the discovered folder |
| Splitting `SolutionValidator` changes the single-pack behaviour | Regressions in the existing Workspaces tests | The existing `SolutionValidatorTests` stay unchanged and must pass at every task |
| Hosts disagree about pack discovery | The "same packs" Definition of Done item fails | Hosts share `IPackSetValidator`; a test per host compares to the CLI output on `twopacks` |
| Blocking on async from a test thread deadlocks under a sync context | A hung test | The sync wrapper runs the async call on the thread pool with `Task.Run` |
