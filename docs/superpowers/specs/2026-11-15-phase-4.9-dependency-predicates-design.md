# Phase 4.9 Design — Dependency predicates and DependOnAny

**Date:** 2026-11-15
**Phase:** 4.9
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-15
**Builds on:** Phase 4.8 — `TargetSelector.AttributeArguments`, `TargetSelector.OnlyAttributes`, `AttributeArgumentMatch`, and `TypeSelector.From(TargetSelector)` compiling both keys, which the nested selector accepts and the 4.8 loader reads with `ReadAttributeArguments`

## Goal

Packs can select and require types by what they depend on. The three #96 catalogue rows, `c-depend-on-any`, `p-depend-on-any` and `p-only-depend-on`, then leave `deferred` with harness cases, and #96 closes.

## Intent

The 2026-11-15 Milestone 4 re-audit failed on criterion 3. Nine type-level catalogue rows are `deferred`, but the criterion allows deferral for member-level kinds only. The owner chose gap phases over amending the criterion. Phase 4.8 takes the six #95 rows and this phase takes the three #96 rows. Criterion 3 allows `out-of-scope` for custom predicates only, so each row needs a pack form and a harness case. #96 asked whether these belong in a pack at all. They do: "the Web types that depend on Infrastructure" is an architectural statement, and a pack could only forbid or confine a dependency, never select or require one.

- **Goal:** one pack form for each of the three rows, valid in rule targets, in `is`/`isNot` and in exceptions, with a harness case per row and polarity. Each case agrees with ArchUnitNET 0.13.5, or has a `Divergences` entry where the tools differ on purpose.
- **Non-goals:** member-level dependencies such as `CallAny`, which #94 tracks. Transitive dependencies. Dependency predicates in layer definitions, `implements` or role definitions. Counting dependencies, such as "depends on at most two".
- **Anti-goals:** a key whose meaning differs between a selector, a condition and an exception. A second notion of "dependency" next to the edges that `forbid`, `allowOnly` and layers already check. Recursion in selectors.

## Approaches

### Pack form

1. **Two new additive selector keys (chosen),** `dependsOn` and `onlyDependsOn`, in the 4.8 pattern. They are valid wherever `attributes` is. Nothing existing changes meaning, so the change is a `feat`.
2. **A new rule kind,** such as `requireDependency`. It covers `c-depend-on-any` only. The two predicate rows need a selector anyway, so the result would be two mechanisms for one idea.
3. **Mark the rows `out-of-scope`.** This needs the owner to amend criterion 3 first, and #96's reasoning above says they belong in a pack.

### Value of the keys

The owner picked option 1 on 2026-11-15.

1. **A nested rule-target selector (chosen).** `dependsOn: { layers: [Infrastructure] }`, `dependsOn: { interfaces: [Shop.IClock] }`. This is closest to ArchUnitNET's `Types().That()…` query and reuses `TargetMatcher`. The cost is in the loader and the schema.
2. **A list of type globs.** Simplest, but it cannot say "a type in layer X" or "a type with attribute Y".
3. **Layer names only.** Short, but the parity fixtures select by namespace, and it cannot express type- or trait-level targets.

## How ArchUnitNET 0.13.5 matches

Read from `ObjectPredicatesDefinition.cs`, `ObjectConditionsDefinition.cs` and `DependencyExtensions.cs` at tag `0.13.5`:

- `That().DependOnAny(X)` keeps a type when one of its dependencies is in `X`. `GetTypeDependencies()` is every dependency target, framework types included. `X` holds architecture types, so framework types only matter when `X` selects them.
- `That().DoNotDependOnAny(X)` is the negation.
- `That().OnlyDependOn(X)` keeps a type when `GetTypeDependencies(architecture).Except(X)` is empty, which counts only dependencies on types of the loaded assemblies. A type with no such dependencies is kept.
- `Should().DependOnAny(X)` passes a type when one of its dependencies is in `X`. `DependOnAnyTypesThat()` takes `X` as a predicate. `Should().NotDependOnAny` and `Should().OnlyDependOn` are the existing rows `c-not-depend-on-any` and `c-only-depend-on`.
- ArchUnitNET reads IL. A type's dependencies include what the compiler emits: the closure class of a lambda (a nested type in the same assembly), the base `System.Object`, attribute classes and generic arguments.

## Decided behaviour

### The keys

```yaml
forbid:
  - id: WEB-NO-INFRA-USERS
    from: { layers: [Web], dependsOn: { layers: [Infrastructure] } }
    to:   { namespaces: [Shop.Web.Pages.**] }
require:
  - id: HANDLERS-USE-CLOCK
    for: { types: ["**Handler"] }
    is:  { dependsOn: { interfaces: [Shop.IClock] } }
  - id: DOMAIN-SELF-CONTAINED
    for: { layers: [Domain] }
    is:  { onlyDependsOn: { layers: [Domain] } }
```

- **`dependsOn: <selector>`** matches a type when at least one of its dependencies is selected by the nested selector.
- **`onlyDependsOn: <selector>`** matches a type when every one of its dependencies **on a type declared in the analysed solution** is selected by the nested selector. A type with no such dependencies matches. Framework and package types never count. This follows ArchUnitNET's `OnlyDependOn`, which counts only the loaded assemblies. Counting framework types would make any use of `string` fail it.

### The nested selector

The nested selector takes the rule-target keys: `namespaces`, `assemblies`, `types`, `layers`, the traits (`names`, `kinds`, `accessibility`, `assignableTo`, `sealed`, `abstract`, `static`, `nested`), `baseTypes`, `interfaces`, `attributes`, and 4.8's `attributeArguments` and `onlyAttributes`. It follows the same rule as a target: `layers` may sit next to traits but not next to glob keys. It may not hold `members`, `dependsOn` or `onlyDependsOn`, so selectors never nest more than one level. An empty nested selector is rejected at load and by the schema.

### What a dependency is

A dependency is a `TypeGraph` edge whose source is the type: one per type reference written in the type's own declaration, with the target as its original definition. That is the same edge set that `forbid`, `allowOnly` and the layer rules check. So:

- a nested type's references belong to the nested type, not to its outer type;
- a self-reference is no dependency, since the walker drops it;
- `var` and an unused `using` give no dependency;
- generated code gives none, apart from the Razor trees that already count as source.

**Scope.** The dependencies of a type are read across the whole run, per target framework scope, as slices already do through `ScopedGraph`. A type declared in another project of the solution, such as a `to` target, has the dependencies that project's graph records for the build this project compiles against. A type declared outside the solution has no dependencies: it never matches `dependsOn` and always matches `onlyDependsOn`.

### Where both keys apply

- Rule targets: `forbid` and `allowOnly` `from` and `to`, `require` `for`, `slices` `allow`, `uniqueNames` `for` and `against`.
- `is` and `isNot`, as `require` conditions with their own messages.
- Exceptions of every rule kind except `bannedPackages`, which rejects them as it rejects `attributes`. This includes amendment exceptions and code-built amendments, through `ExceptionKeyRules.UsedKeys`.
- Unlike 4.8's keys, both **may sit next to `layers`**, as traits do. This is a call made for this design. "The Web types that depend on Infrastructure" is the main architectural use, and `{ layers: [Web], dependsOn: { layers: [Infrastructure] } }` says it directly. They join the trait-like keys, not `OtherSelectorKeys`.
- Not in `implements`, layer definitions or roles.

Each key alone makes a selector or an exception non-empty. `RulePackReferenceCheck` checks the nested selector as it checks a target, so an unknown layer inside `dependsOn` is reported at its path, and the "needs at least one of …" messages list both keys. `VacuityRules` needs no change: a rule whose `dependsOn` selects nothing selects no type, and is reported as it is today.

### Messages

`RequireCondition` gets one condition per key:

- `dependsOn`: "should depend on a type matching <description of the nested selector> but does not". Under `isNot`: "should not depend on a type matching … but depends on 'Shop.Infrastructure.SqlStore'", naming the first matching dependency in source order.
- `onlyDependsOn`: "should only depend on types matching … but depends on 'Shop.Infrastructure.SqlStore'", naming the first dependency outside the set in source order. Under `isNot`: "should not only depend on types matching … but does".

The description of the nested selector comes from `RulePackDescriber`, which describes both keys.

## Model (Abstractions)

- `TargetSelector` and `RuleException` each get `TargetSelector? DependsOn` and `TargetSelector? OnlyDependsOn`.
- The generated validators reject a nested selector that itself holds `DependsOn`, `OnlyDependsOn` or `Members`, or that is empty. If ZeroAlloc.Validation does not validate a nested `[Validate]` object, a `Must` method validates it by hand, as `HasNoNullEntries` does for lists.
- Abstractions stays AOT-compatible with no new dependency.

## Analysis

- **Dependency index.** A new `DependencyIndex` maps a type, per target framework scope, to its dependency targets in source order. It is built from all graphs of the run before the per-project checks. A metadata symbol of another project's type is found in that project's graph by assembly and metadata name, because the symbols of two compilations are not equal.
- **Validator order.** `ArchitectureValidator` today builds each project's graph and checks it in one step (`AnalyzeProject`). It now builds every graph first, then the index, then runs the per-project checks. A pack that uses neither key builds no index, so its runs are unchanged.
- **Selectors.** `TypeSelector` compiles `dependsOn` and `onlyDependsOn` into nested `TargetMatcher`s. `Matches` reads the type's dependencies from the index of the current scope. `TargetMatcher` allows them next to `layers`. The per-type match cache stays valid, because a type symbol belongs to one compilation and so to one scope.

## Tests

- **Loader:** each key loads into its property in a target next to `layers`, in a condition and in an exception. Every rejection above is reported at its line and column. An unknown layer inside a nested selector is reported by `RulePackReferenceCheck` at its path. An amendment exception with either key merges, and a code-built amendment with either key on an inherited `bannedPackages` rule is rejected.
- **Analysis:**
  - `DependencyIndex` gives a type's targets in source order and drops self-references.
  - A nested type's references are its own.
  - A metadata type of another project in the run has that project's dependencies, and a type outside the solution has none.
  - Two target frameworks of one project keep separate dependencies.
  - `TypeSelector` covers `dependsOn` on one matching dependency and on none; `onlyDependsOn` with all inside, one outside, only framework dependencies and no dependencies; and both keys next to `layers`.
  - `RequireCondition` covers both messages and both polarities.
  - A validator test proves that a pack without either key builds no index.
- **Schema:** the `PackSchema` valid and invalid cases above. The harness fails when the schema and the loader disagree.
- **Parity:** four cases, one per row and polarity.
  - `p-depend-on-any`: `That().DependOnAny(Target)` with `Should().NotDependOnAny(Forbidden)`, against `forbid` `from: { namespaces, dependsOn: { namespaces: [….Target.**] } }`.
  - `p-depend-on-any:not`: `That().DoNotDependOnAny(Target)` against a `forbid` from the kind's namespaces, with an exception that holds `dependsOn`.
  - `c-depend-on-any`: `Should().DependOnAny(Target)` against `require` with `is: { dependsOn }`. There is no `:not` case: `NotDependOnAny` is `c-not-depend-on-any`.
  - `p-only-depend-on`: `That().OnlyDependOn(Allowed)` against `forbid` `from: { namespaces, onlyDependsOn }`. ArchUnitNET has no negation of this predicate.
- **IL measurements:** each fixture also holds three probe types:
  - one whose only other dependency is a lambda's compiler-generated closure class;
  - one that depends only on framework types;
  - one with no dependencies.

  When ArchUnitNET and Ariadne disagree on a probe, the probe moves into its own folder and its case gets a `Divergences` entry. The expected answer is Ariadne's, because a developer reads dependencies from the code they wrote. The row then becomes `divergence`. When the tools agree, the row is `covered`.
- **Docs:** `CatalogueConsistencyTests`, `MigrationGuideSnippetTests` and `MigrationGuideTests` pass, and the guide's new YAML blocks load.

## Settled in the builder check

A builder read this design before approval. Each answer below is a call made for this design, grounded in the code or in ArchUnitNET's behaviour:

- **Nested types are not special-cased.** A type that references its own nested type depends on it, and `onlyDependsOn` needs the nested selector to select the nested type, as ArchUnitNET's `Except(X)` does. A nested type usually shares its outer type's namespace, layer and assembly, so `onlyDependsOn: { layers: [Domain] }` still holds.
- **Generic arguments are dependencies.** `TypeReferenceWalker.AddEdgesForWrittenType` already gives one edge per type argument, array element, tuple element and `T?` part. So `IEnumerable<IClock>` depends on both `IEnumerable<>` and `IClock`.
- **Types outside the solution can be dependencies.** A framework or package type is the target of an edge, and the nested selector matches it with any key that reads a metadata symbol: `namespaces`, `assemblies`, `types`, `layers`, the traits, `baseTypes`, `interfaces` and the attribute keys. `dependsOn: { namespaces: [System.Net.Http.**] }` selects the types that use `HttpClient`. Only `onlyDependsOn` ignores such dependencies.
- **Where the nested selector is compiled.** A nested selector is compiled into a `TargetMatcher` by the rule compiler that holds the `LayerMap`: `ForbidRules`, `AllowOnlyRules`, `RequireRules`, `SliceRules`, `UniqueNameRules`, `VacuityRules`, and the exception paths of each. `TypeSelector` then receives the compiled nested matchers, and is not asked to build them. So `TypeSelector.From(RuleException)` and `From(TargetSelector)` gain an overload or parameter that carries the `LayerMap`, and an exception's `dependsOn` may use `layers`. These signatures are internal, so the change is not breaking.
- **Matching a metadata symbol to its producer.** The index is keyed by the symbol's containing assembly name and its metadata name, nested types included, as `TypeNames` and Roslyn's `MetadataName` give them, and found through the current scope's `ScopedGraph.References`. A type of a run project that the current scope does not reference cannot appear as a symbol there. A forwarded type resolves to its destination before lookup.
- **An empty dependency set.** `onlyDependsOn` holds for a type with no solution dependencies. So `isNot: { onlyDependsOn }` fails every such type, with "should not only depend on types matching … but does". This is the negation applied as written, and a unit test pins it.
- **The `p-only-depend-on` parity rule.** It follows the other predicate cases: `Types().That().OnlyDependOn(Allowed).Should().NotDependOnAny(Target)` against `forbid` `from: { namespaces: [<kind>.**], onlyDependsOn: { namespaces: [<kind>.Allowed.**] } }` and `to: { namespaces: [<kind>.Allowed.Target.**] }`. `Target` lies inside the allowed set, so a type that depends on `Allowed.Target` alone is selected and flagged (`Broken`). A type that depends on `Allowed.Target` and on a type outside `Allowed` is not selected and passes (`Clean`). The probe types sit in `Clean` or `Broken` according to what each tool selects.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Splitting graph building from checking keeps every graph alive at once | Higher peak memory on large solutions | `UniqueNameRules`, `SliceRules` and `VacuityRules` already hold all graphs after the loop, so the peak barely moves. Re-check with `tools/perf` and note the result in the plan's last task |
| A metadata symbol cannot be matched to its producer's source symbol | `to` targets in other projects never match `dependsOn` | Match by assembly and metadata name inside the scope's referenced graphs, as `ScopedGraph` already pairs references with producers. A test covers it |
| ZeroAlloc.Validation cannot validate a nested `[Validate]` object | Weaker validation for code-built packs | Validate by hand in a `Must` method. The AOT smoke test must stay green |
| ArchUnitNET counts compiler-generated dependencies | One or more rows become `divergence` | The fixtures measure it on purpose with probe types, and the result is recorded as a `Divergences` entry. Criterion 3 accepts `divergence` |
| Keys allowed next to `layers` diverge from 4.8's attribute keys | Users may expect `attributes` there too | Documented in the rule-schema page. Widening the attribute keys is outside this phase |
