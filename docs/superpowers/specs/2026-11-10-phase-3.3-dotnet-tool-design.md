## Goal

`dotnet tool install Ariadne.NET.Cli` gives an `ariadne` command that validates a solution and runs the agent hooks, built and checked by CI before every release, and pushed by `publish-nuget`.

## Approach

**Package.** `src/Ariadne.NET.Cli/Ariadne.NET.Cli.csproj` becomes packable: `IsPackable` true, `PackAsTool` true, `ToolCommandName` `ariadne`, `PackageId` `Ariadne.NET.Cli`, a description, a `PackageReadmeFile` (a new `README.md` next to the project), and the shared metadata from `Directory.Build.props` (license, repository, symbols). It stays framework-dependent on .NET 10; there is no AOT or trimming because MSBuild is located at run time. `PackAsTool` bundles the project references (`Ariadne.NET`, `Ariadne.NET.Workspaces`, `Ariadne.NET.Hooks`, their dependencies) into the tool's `tools/net10.0/any/` folder, so the tool's version stands alone and the package has no NuGet dependencies on the other Ariadne packages. `Ariadne.NET.Mcp` and `Mcp.Http` stay unpackaged.

**MSBuild assemblies.** The CLI already carries `Microsoft.Build.Framework` with `ExcludeAssets="runtime"` so `MSBuildLocator` loads the SDK's copy. The packed tool must keep that property: no `Microsoft.Build*` assembly other than the BuildHost folders from `Microsoft.CodeAnalysis.Workspaces.MSBuild` may sit in `tools/net10.0/any/`. The inspection script checks this for the tool package.

**Inspection.** `tools/release/inspect_packages.py` today demands exactly the library packages with their dependency edges. It learns a fifth package, `Ariadne.NET.Cli`, with tool-specific rules: the package is of type `DotnetTool` (`DotnetToolSettings.xml` with `Command Name="ariadne"` and a runner), its `.nuspec` has no Ariadne dependencies (everything is bundled), the compiled informational version of `ariadne.dll` or `Ariadne.NET.Cli.dll` matches the release version, no `Microsoft.Build.*` DLL is bundled apart from the Workspaces build host files, and the `.snupkg` exists. The script's own tests get a case for each rule.

**pack-validate.** The job already packs the slnx and pushes to a local feed. A new step installs the tool from that feed into a temp folder (`dotnet tool install Ariadne.NET.Cli --tool-path <dir> --add-source <feed> --version $PACKAGE_VERSION`) and runs: `ariadne --version` (must print the release version), `ariadne validate` on `tests/fixtures/twopacks` with `--format json` (must exit exactly 1, stdout must parse as JSON with `"schema": 1`, and must name the broken pack), and `ariadne validate` on a clean fixture (must exit 0). It also runs `ariadne hook session-start` with an empty JSON object on stdin and expects exit 0, which proves the hook entry point runs in the packed tool. Fixtures are restored first with a normal `dotnet restore` on the runner.

**publish-nuget.** It already runs `dotnet pack src/Ariadne.NET.slnx`, which packs the tool once it is packable, and pushes `artifacts/packages/*.nupkg`; the inspect step already covers it. Changes: the failure message text and `RELEASING.md` name five packages; the trusted publishing policy note says the new package ids (`Ariadne.NET.Testing` from 3.1 and `Ariadne.NET.Cli`) must be allowed as new ids on nuget.org, which the owner checks before the first release containing them. The workflow does not change shape.

**Docs.** The getting-started page gains "Install the tool" with `dotnet tool install --global Ariadne.NET.Cli`, `ariadne --version` and the first validate; the hooks page (written in 5.6) is checked for the `PATH` assumption and linked to the install section. The Milestone 5 hooks item in ROADMAP.md stays as it is; its owner ticks it after release.

## Tests

- Unit: `--version` prints the informational version without the `+` metadata; the inspection script test cases for the tool (type, no Ariadne dependencies, wrong command name, bundled `Microsoft.Build.dll`, wrong version, missing symbols).
- Integration: locally, `dotnet pack src/Ariadne.NET.Cli -c Release -p:AriadneRelease=true -o <temp>` and the inspection script on the result; this is the same pack the CI runs. The install-and-run steps are exercised by `pack-validate` in CI; running them locally is optional and must not use the global tool folder (use `--tool-path`).
- Regression: the existing Cli tests and the slnx build still pass with the project packable.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The tool bundles the wrong MSBuild assemblies | `ariadne validate` fails after install | The inspection rule plus `validate` on a fixture in `pack-validate`, not only `--version` |
| `PackAsTool` plus project references duplicates the library DLLs and breaks MSBuildLocator | The tool starts and cannot load a solution | Same fixture run; the first CI run is the proof |
| `ariadne hook` writes to a per-user folder in CI | A leftover file | The hook smoke uses `session-start`, which writes nothing |
| The new package ids are refused on nuget.org | The release fails after the first push | RELEASING.md tells the owner to check the Trusted Publishing policy first |
