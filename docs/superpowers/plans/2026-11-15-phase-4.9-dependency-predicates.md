# Phase 4.9 — Dependency Predicates and DependOnAny Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Packs select and require types by what they depend on (`dependsOn`, `onlyDependsOn`), so the three #96 catalogue rows leave `deferred` with harness cases and #96 closes.

**Architecture:** Abstractions gets two nested `TargetSelector?` properties on `TargetSelector` and `RuleException`. The validator builds every graph first, then a run-wide `DependencyIndex`, and only then compiles and runs the rules, so each rule compiler can turn a nested selector into a `TargetMatcher` that reads the index. The loader, `RequireCondition`, the describer, the schema, the parity fixtures, the catalogue and the docs follow.

**Tech Stack:** .NET 10, Roslyn, YamlDotNet representation model, ZeroAlloc.Validation 2.5.0, xUnit + FluentAssertions, TngTech.ArchUnitNET 0.13.5 (parity harness).

**Spec:** `docs/superpowers/specs/2026-11-15-phase-4.9-dependency-predicates-design.md`

**Builds on:** Phase 4.8. The nested selector accepts `attributeArguments` and `onlyAttributes` (`TargetSelector.AttributeArguments`, `TargetSelector.OnlyAttributes`, `AttributeArgumentMatch`), and `TypeSelector.From(TargetSelector)` compiles them. The 4.8 loader reads them with `ReadAttributeArguments`.

## Global Constraints

- Key names: `dependsOn` and `onlyDependsOn`. Model: `TargetSelector? DependsOn` and `TargetSelector? OnlyDependsOn` on both `TargetSelector` and `RuleException`.
- The nested selector takes the rule-target keys: `namespaces`, `assemblies`, `types`, `layers`, the `TraitKeys`, `baseTypes`, `interfaces`, `attributes`, `attributeArguments` and `onlyAttributes`. It may not hold `members`, `dependsOn` or `onlyDependsOn`, and an empty one is rejected. `layers` may sit next to traits but not next to glob keys, as in a target.
- The two keys may sit next to `layers`, as traits do. They are valid in rule targets (`forbid`/`allowOnly` `from` and `to`, `require` `for`, `slices` `allow`, `uniqueNames` `for` and `against`), in `is`/`isNot`, and in exceptions. They are not valid in a `bannedPackages` exception, `implements`, layer definitions or roles.
- A dependency is a `TypeGraph` edge whose `Source` is the type: targets as original definitions, in source order, with no duplicates. A type declared outside the run's projects has no dependencies.
- `dependsOn` holds when one dependency is selected. `onlyDependsOn` holds when every dependency on a type declared in a run project is selected, and on an empty set.
- A pack that uses neither key builds no index, and its run is unchanged.
- The change is additive: commits are `feat`/`refactor`/`test`/`docs`. Commit bodies have no nested parentheses. `TreatWarningsAsErrors` is on. Do not run the AOT publish locally; CI's `aot-smoke` job proves Abstractions.
- The new public API in Task 1 was approved by the owner on 2026-11-15 as part of the approved design; an unattended run builds it.

## Review Focus

- A `to` target declared in another project of the solution must use that project's dependencies, not report none. (Task 2 test.)
- A project built for two target frameworks must not mix the dependencies of its two builds. (Task 2 test.)
- `onlyDependsOn` must ignore a dependency on `System.String`, but `dependsOn: { namespaces: [System.**] }` must still select a type that uses it. (Task 4 test.)
- An exception's `dependsOn: { layers: [...] }` must work, although `RuleException` itself has no `layers`. (Task 4 test.)
- A pack without either key must not pay for the index: `UsesDependencyKeys` is false and no `DependencyIndex` is built. (Task 3 test.)
