# Phase 4.7 — Attributes in Rule Exceptions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rule exceptions and amendment exceptions accept `attributes`, with the meaning the selector key has, so `p-have-any-attributes:not` is covered and #97 closes.

**Architecture:** `RuleException` gets an `Attributes` list next to the traits. The loader reads it with `Glob.Dotted`, and `ExceptionKeyRules` allows it everywhere except `bannedPackages`. `TypeSelector.From(RuleException)` passes it into the attribute slot of the existing `Compile` call. Then the schema, the parity fixture, `KnownGaps`, the catalogue and the docs follow.

**Tech Stack:** .NET 10, Roslyn, YamlDotNet representation model, ZeroAlloc.Validation, xUnit + FluentAssertions, ArchUnitNET 0.13.2 (parity harness).

**Spec:** `docs/superpowers/specs/2026-11-14-phase-4.7-attributes-in-rule-exceptions-design.md`

## Global Constraints

- `attributes` in an exception means the same as in a selector: dotted globs (`Glob.Dotted`) over the full name of each attribute class's original definition that is applied directly to the type. Any one glob may match, and the keys of one exception are AND-ed.
- Only `attributes` joins exceptions. `baseTypes` and `interfaces` stay out.
- A `bannedPackages` exception rejects `attributes` with the existing reason: `a package belongs to a project, so the exception of a bannedPackages rule names it by 'assemblies'`.
- Key order wherever keys are listed: `namespaces`, `assemblies`, `types`, `attributes`, then the eight traits.
- The change is additive: commits are `feat`/`test`/`docs`, and no breaking footer is needed. Commit bodies have no nested parentheses.
- `TreatWarningsAsErrors` is on, so the build stays at zero warnings.

## Review Focus

- An exception with only `attributes` must count as selecting something. It must not fail with "needs at least one of …". (Task 1 test.)
- An amendment exception with `attributes`, both from YAML and built in code, must merge, and a code-built one on a `bannedPackages` rule must fail. (Task 1 tests.)
- A type that carries the attribute only through a base class is not exempt, because the selector reads direct attributes. (Task 2 test.)
- A malformed glob such as `"A..B"` in an exception's `attributes` is reported at its line, as in the selector. (Task 1 test.)
- The schema's bannedPackages `if`/`then` must bar `attributes`, or the schema accepts what the loader rejects. (Task 3 invalid pack.)
