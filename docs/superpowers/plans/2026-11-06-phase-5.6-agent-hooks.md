# Phase 5.6 Agent hooks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `ariadne hook session-start|pre-tool-use|stop` gives a Claude Code agent the resolved structural rules at session start, a question before a new `.cs` file outside every layer, and the validator's violations with each rule's reason at the end of a turn; `ariadne init --agent claude` installs the three hook entries.

**Architecture:** A new library `Ariadne.NET.Hooks` holds the hook logic behind one entry, `HookHost.RunAsync`, which reads the event JSON, runs the matching `IHook` and fails open on any internal error. The `hook` CLI command and `init --agent claude` are thin wrappers in `Ariadne.NET.Cli`. The engine gains two small additions that both the hooks and the CLI use: `RulePackDescriber` (rule text, extracted from `RulesCommand`) and `LayerProbe` (layers selected by an assembly name and a namespace).

**Tech Stack:** .NET 10, System.CommandLine 3.0 rc, System.Text.Json (`JsonDocument`/`Utf8JsonWriter`, no reflection), xUnit + FluentAssertions, the repo's analyzers at zero warnings.

**Spec:** `docs/superpowers/specs/2026-11-06-agent-guidance-hooks-design.md` (stage A). Hook field names were checked against https://code.claude.com/docs/en/hooks on 2026-11-06.

## Global Constraints

- Branch `docs/agent-hooks-design`; push only with `git push ariadne HEAD:docs/agent-hooks-design`, never to `origin`.
- Commits: conventional (types in `.commitlintrc.yml`, subject not sentence-case), no `Co-Authored-By` trailer, no session link, no nested parentheses in a body, every footer line under 100 characters. Nothing in this plan is breaking.
- Fail open: any internal error in a hook is one line on stderr and exit code 0 with empty stdout. Never exit 2 from a hook: on `PreToolUse` that blocks the tool call, and `CliRootCommand.InvokeAsync` turns an uncaught exception into exit 2.
- A hook never touches the network. "Stale cache" is decided offline: the cached `resolvedTag` in `.architecture/.cache/git/<name>/.git-info.json` no longer satisfies the import's `version` range (`SemVerRange`), or the cache directory is absent.
- Each injected context string is at most 10,000 characters (Claude Code replaces longer output with a file path and a preview).
- `PreToolUse` only ever returns `ask`, never `deny`, and only for a new `.cs` file whose assembly and namespace no layer selects.
- `Ariadne.NET` (Core) must not reference `Ariadne.NET.Hooks`; `Ariadne.NET.Abstractions` is untouched and stays AOT-compatible. No dependency on AI.Sentinel.
- Repo conventions: one type per file, `ConfigureAwait(false)`, `IList`/`IReadOnlyList` in public APIs, explicit string comparers, `TreatWarningsAsErrors`. One build or test at a time on the shared VM; no local AOT publish.
- Hook wire format (Claude Code, verified): stdin JSON carries `session_id`, `transcript_path`, `cwd`, `hook_event_name`; `PreToolUse` adds `tool_name` and `tool_input` (`Write`: `file_path`, `content`; `Edit`: `file_path`, `old_string`, `new_string`); `Stop` adds `stop_hook_active` (bool). Output on stdout, exit 0: `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"..."}}`; `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"ask","permissionDecisionReason":"..."}}`; `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"..."}}` (feedback that continues the turn without a hook-error label; capped by `stop_hook_active` and Claude Code's 8-continuation cap).

## Decisions this plan makes beyond the spec

These are for the owner to confirm at review.

1. **Attachments (`standards`, `skills`, `files` on `RulePack`) are not in this plan.** The spec says stage A loads and merges them, but without Guidance nothing interprets them and they would change the Abstractions schema for no user. They become Task 1 of the 5.7 plan. The roadmap's 5.6 goal does not mention them.
2. **"Edited `.cs` files this turn" is tracked by the `pre-tool-use` hook**, which appends the path to a per-session file in the temp folder; `stop` reads and clears it. `Stop` input has no edit list, and parsing the transcript is fragile. No fourth event, no `PostToolUse`.
3. **`stop` feeds back with `additionalContext`, not `decision: block`**, so the agent continues without a hook-error label. It stays silent when `stop_hook_active` is true (once per turn) and clears the edit list then.
4. **The spec's "existing layer inference" does not exist for paths**: `LayerInferenceEngine` maps a role name to a layer. The new-file check derives an assembly name and namespace from the nearest `.csproj` and the folder, and asks `LayerProbe`. Task 4 has a no-noise gate over real code; if it cannot be made to pass, drop `pre-tool-use` from stage A, as the spec allows.
5. **`Ariadne.NET.Hooks` is `IsPackable=false` for now**; 5.7 flips it when Guidance needs to reference it.
6. **Namespace for the new-file check comes from the content.** For `Write`, `tool_input.content` is parsed for a `namespace X;` or `namespace X {` declaration; the folder-derived namespace is only the fallback. The folder alone is wrong in real code (`Daedalus.Agents/RagAgent.cs` declares `Daedalus.Agents.Runtime.Retrieval`). `Edit` of an existing file is never checked.
7. **`stop` reports every violation in the solution, not only those in edited files**, and its header says so. Filtering by `Location.FilePath` would hide violations the edit caused in other files (a changed type breaking a dependent). The 20-violation cap keeps it short. Say if you want the filter.
8. **`init --agent claude` keeps an existing `.architecture/rules.yaml`** and only adds the hooks; without `--agent`, `init` still overwrites as today.
9. **The first `init --agent claude` run reformats an existing `settings.json`** (2-space indent, relaxed escaping); later runs are byte-identical.
10. **`ariadne` is not a dotnet tool until phase 3.3.** `init --agent claude` writes the spec's `ariadne hook <event>` command regardless; until 3.3 lands it works only where an `ariadne` executable is on PATH. Tests never run the entries.

## Review Focus

Inputs the spec implies but its goals do not exercise, most likely first; each has a test in the named task.

1. Empty, truncated or non-JSON stdin, and an unknown event name: exit 0, empty stdout, one stderr line (Task 1).
2. Project without `.architecture/rules.yaml`: `session-start` says so and names `ariadne init`; `pre-tool-use` and `stop` are silent (Tasks 3, 4, 5).
3. Zero or several solutions, or a solution that fails to load: `stop` is silent and warns on stderr (Task 5).
4. `.claude/settings.json` that is invalid JSON, or holds the user's own hooks and other keys: `init` never overwrites it and never touches foreign entries; a second run changes nothing (Task 7).
5. Windows-style `file_path` with backslashes, paths with spaces, and a pack large enough to pass the 10,000-character cap or yield hundreds of violations: output is cut with a visible "run `ariadne rules`" or "and N more" line, never silently (Tasks 3, 5).
